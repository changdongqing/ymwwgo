## 1. 背景与范围

### 1.1 需求起点：从量纲反查计量单位

计量域种子（goose `00005`）落库后，单位个体以 61 号对象属性断言挂接量纲：`摄氏度 --hasQuantityKind--> 温度`。用户需要**反向**浏览："温度这个量纲被哪些单位挂接？"——这是 OWL 中任意 `?s P ?o` 边的自然反向读法，而不是单位的专有字段。

本仓现状实测（dev 库，2026-10-23）：

```sql
-- 目标：温度(id=341) 被谁挂接
SELECT subject_id, predicate_iri FROM ont_axioms
WHERE ontology_id=7 AND object_id=341 AND axiom_type=61 AND deleted_at IS NULL;
-- 401 摄氏度、403 华氏度（谓词 …#hasQuantityKind）

EXPLAIN -- Bitmap Index Scan on idx_ont_axioms_object, Index Cond: (ontology_id=7 AND object_id=341)
```

即：**数据层已经能答案这个问题，且走现成索引**；缺的是把它变成可浏览、可过滤、可分页的一等读能力。全库 61 行当前 188 条、3 个谓词（`hasQuantityKind` / `scalingOf` / `conventionalUnit`），规模验证无压力。

### 1.2 现状能力盘点（为什么"有反查"却"不像通用设计"）

| 层 | 现有物 | 事实 |
|---|---|---|
| 存储 | `ont_axioms` 边表 | 每条公理即一条边/元组；61 行 `subject_id`+`predicate_iri`+`object_id`，**不成对存储**（`internal/ontology/types.go:50`），反查是唯一来源 |
| 索引 | `idx_ont_axioms_object (ontology_id, object_id)` | 目标侧反查现成可用；另有 `(ontology_id, subject_id, axiom_type)` 与 `(ontology_id, axiom_type, value_text text_pattern_ops)` |
| 数据层 | `OntAxiomRepo.ListByObject`（`data/ontology_axiom_repo.go:61`） | 返回目标侧全部未删公理行，**无类型过滤、无分页** |
| 数据层 | `ListByPredicateIRI`（`:157`） | 谓词侧反查（谁用了这个属性），**无分页** |
| 服务层 | 六类实体各一个 `Usage` RPC（class/object-property/data-property/annotation-property/datatype/individual） | 共用 `EntityUsage` / `EntityUsageRef`（`ontology.proto:77-103`）；proto 注释定位即"谁引用了我" |
| 服务层 | 个体 `Usage`（`ontology_individual_service.go:471`） | 只查 61、**丢弃谓词**、按引用方去重 |
| 服务层 | 对象属性 `Usage`（`ontology_object_property_service.go:345`） | 已含 30/34/35/36 + 37 链成员 + 61 谓词反查（`predicate_iri` 命中）——谓词反查已兑现，但仍去重、无分页 |
| 前端 | 六个页面各写一遍 usage hook | 只在**删除确认**的 usage 弹窗消费；实体详情/抽屉里没有"被引用"视图 |

结论：反查被定格成"删除保护计数"——回答"有没有人用我"，回答不了"通过哪条属性、有哪些边、能不能翻页浏览"。六个 `Usage` 平行实现也是"每类实体配一份"的重复模式，不是通用设计。

### 1.3 缺口清单（本文要解决的）

1. **谓词丢失**：`EntityUsageRef` 只有 `entityId/localName/displayLabel/axiomType`，看不到"哪条对象属性/数据属性"。
2. **无分页/无过滤/无排序**：多值关系（一个量纲↔多个单位）无法浏览。
3. **函数式去重**：`refs` 是"引用方实体集合"，不是"边"——同一对实体间多条不同谓词的边会被压成一条。
4. **六份平行实现**：新增实体类型还要再配一个 `Usage`。
5. **无界面承载**：删除弹窗之外无处查看；用户只能绕过 UI 用 SQL/接口。

### 1.4 范围声明

**V1 做**：通用反向边查询（目标实体侧，只读）、单端点、边级明细（主语/谓词/宾语或字面量/公理类型）、分页与过滤、与 `Usage` 共用数据层、前端共享「被引用」面板挂六类实体抽屉。

**V1 显式不做**（决策记录，防范围回潮）：

| # | 不做项 | 理由与出路 |
|---|---|---|
| 1 | 正向边查询端点 | 正向读取已由各实体 `Frame`/编辑表单承载，重复建设 |
| 2 | 通用图查询 DSL / SPARQL 子集 | 需求是"反查某目标"，边级过滤足够；查询语言是独立大工程，V3 再议 |
| 3 | 推理/传递闭包（如量纲自身层级 `broaderQuantityKind` 的自动展开） | 本仓 V1 无推理机（01 号决策五）；`includeDescendants` 仅复用例的 60/20 结构子树，不做个体层闭包 |
| 4 | 反查结果就地编辑/删除边 | 只读投影；编辑走各实体既有抽屉（同一批 axiom 行，写路径不重复建设） |
| 5 | 跨本体反查 | `validateRefEntities` 本就禁止跨本体引用，无此场景 |
| 6 | 新增错误码段（如 90~96） | 只读查询的错误都能映射到现有 `BadRequest`/`ENTITY_NOT_FOUND`/`ONTOLOGY_NOT_FOUND`；确需专属 reason 时按 01 号文档号段纪律回填（§10） |

## 2. 关键架构决策

### 2.1 决策一：返回物是"边"，不是"实体清单"

`Usage` 的去重实体集合是删除保护的产物（"有没有人引用"）；通用反查必须回答"哪条边"——同一主语经不同谓词指同一目标时是两条边、不可压。故响应模型升级为 `ReferenceEdge`（§5.1），这是本文与既有 `Usage` 的本质区别，也是唯一不能省的设计点。

### 2.2 决策二：单端点，ontology 级服务；不按实体类型复制 Usage 模式

新增 `OntologyReferenceService`（一个 RPC `ListReferences`），参数化 `targetId + axiomTypes + predicateIri + positions`，覆盖六类实体的全部反查场景。**不为类/属性/数据类型各配一个 References 端点**——那正是现有 `Usage` 六份平行的老问题。实体类型的差异由 `axiomTypes` 参数承载，而不是由端点承载。

`positions` 解决"目标在行内的位置"这一维度：反查的语义是"**哪些边引用了目标实体**"，而引用可能发生在宾语位（`object_id`，主用例）、谓词位（`predicate_iri`，如"谁用 hasQuantityKind 断言"）或属性链成员位（37 的 `value_text`）。现有对象属性 `Usage` 的"被引用"本就同时统计这三种位置（`ListByPredicateIRI` + `ChainReferrers`），通用端点必须保留这一语义，否则属性抽屉的「被引用」会少一半数据。proto 枚举名按 buf lint 的 `ENUM_VALUE_PREFIX` 规则加 `REFERENCE_POSITION_` 前缀、零值补 `_UNSPECIFIED`（实现修订 #1）。

### 2.3 决策三：只读投影，零新表、零写入、零变更日志

反查不产生新事实，只是 `ont_axioms` 的另一个读向。不写 changelog、不动 `ont_ontologies.version`；与 07 期导出同源（同一批行），因此**不存在与 OWL 导出的语义漂移**。

### 2.4 决策四：`Usage` 保留原有语义，内部下沉共用数据层

六个 `Usage` RPC 的对外契约（去重、类型集、`EntityUsage` 形状）一律不变——它们是删除保护的一部分，前端弹窗依赖其"引用方列表"语义。实现上下沉到与 `ListReferences` 相同的 repo 方法（仅选列/排序差异），避免"删除保护反查"和"浏览反查"两套查询逻辑各自演化（历史教训：06 期 classId 过滤恒空即两段式查询的置位次序在单一实现内的疏漏）。

### 2.5 决策五：`owl:inverseOf`（34）只做展示增强，不作反查前提

逆属性在 34 行成对存储（`types.go:37`），但 **61 断言不存逆边**。若未来在对象属性上声明了逆属性，面板可把方向标题渲染成逆属性名（如"被挂接量纲"），那是锦上添花；通用反查永远直接读目标侧，不依赖任何逆属性声明——否则"未声明逆属性就无法反查"，与 OWL 语义不符（反查是查询方向，不是公理）。

### 2.6 决策六：索引一期复用、二期按需迁移；引用查询不走全文扫描

一期全靠 `idx_ont_axioms_object`；`predicate_iri` 过滤在一期是**索引内过滤**（目标已收敛到很少的边，直线可接受）。二期若出现"按属性反查海量断言"场景（例如测点建模后 61 边达十万级），再加 `(ontology_id, axiom_type, predicate_iri)` 索引（goose `00006` + Ent schema 同步，§3.4）。不以"可能要用"为由提前加索引。

## 3. 数据模型

### 3.1 一期零 DDL

不新增表、不新增列、不改索引。查询完全建立在 01 号文档 §3 的既有四表上。

### 3.2 边模型：公理号段 × 反查可用性矩阵

反查的语义是"哪些边引用了目标实体"，目标在行内的**位置**有三种（由请求参数 `positions` 选择）：

| position | 匹配方式 | 典型语义 |
|---|---|---|
| `REFERENCE_POSITION_OBJECT`（默认） | `object_id = targetId` | 目标作为宾语：量纲被单位挂接、类的属性/子类/实例、属性被用作域值域 |
| `REFERENCE_POSITION_PREDICATE` | `predicate_iri = target.iri`（仅 61；100-IRI 轨 V1 不做） | 目标属性被用作断言谓词："谁在用 hasQuantityKind 断言" |
| `REFERENCE_POSITION_CHAIN_MEMBER` | 37 行 `value_text` JSON 数组成员 = targetId | 目标属性出现在某超属性的属性链里 |

`target_id` 的宾语位反查语义如下（以"目标实体"为视角）：

| axiom_type | 语义 | 目标在行内位置 | 反查结果 | V1 默认集 |
|---|---|---|---|---|
| 20 子类 | subject=子类，object=父类 | `object_id` | 类的直接子类 | ✓ |
| 21 不相交 | 成对两行 | `object_id` | 与目标不相交的类 | ✓（成对去重） |
| 22 等价类 | 成对两行 | `object_id` | 与目标等价的类 | ✓（成对去重） |
| 30 子对象属性 | subject=子属性，object=父属性 | `object_id` | 以目标为父属性的子属性 | ✓ |
| 31 对象属性定义域 | subject=属性，object=类 | `object_id` | 定义域含目标的属性 | ✓ |
| 32 对象属性值域 | 同上 | `object_id` | 值域含目标的属性 | ✓ |
| 33 对象属性特征 | subject=属性，predicate_iri=特征 IRI | 非实体边 | 特征 IRI 文本（无实体可填） | ✗（显式请求时渲染 IRI 文本） |
| 34 逆属性 | 成对两行 | `object_id` | 与目标互逆的属性 | ✓（成对去重） |
| 35 等价对象属性 | 成对两行 | `object_id` | 与目标等价的属性 | ✓（成对去重） |
| 36 不相交对象属性 | 成对两行 | `object_id` | 与目标不相交的属性 | ✓（成对去重） |
| 37 属性链 | subject=超属性，value_text=链成员 id JSON 数组 | **`value_text` 内** | 链中包含目标的超属性 | ✓（复用 `ontology.ChainReferrers`，专用解析） |
| 40 子数据属性 | subject=子属性，object=父属性 | `object_id` | 以目标为父属性的子属性 | ✓ |
| 41 数据属性定义域 | subject=属性，object=类 | `object_id` | 定义域含目标的数据属性 | ✓ |
| 42 数据属性值域 | 双轨：内建 IRI 在 value_text / 派生实体在 object_id | 两轨 | 值域是目标的属性（派生轨）；目标为内建 IRI 时无实体反查 | ✓（派生轨命中；内建轨不进默认集） |
| 43 数据属性特征 | subject=属性，predicate_iri=特征 IRI | 非实体边 | 同 33 | ✗ |
| 44 等价数据属性 | 成对两行 | `object_id` | 与目标等价的属性 | ✓（成对去重） |
| 45 不相交数据属性 | 成对两行 | `object_id` | 与目标不相交的属性 | ✓（成对去重） |
| 46 数据类型定义 | subject=datatype，value_text=JSON | 无目标归边语义 | — | ✗ |
| 50 子注解属性 | subject=子属性，object=父属性 | `object_id` | 以目标为父的注解属性 | ✓ |
| 60 类型断言 | subject=个体，object=类 | `object_id` | 目标类的实例个体（`includeDescendants` 时含子类实例） | ✓ |
| **61 对象属性断言** | **subject=个体，predicate_iri=属性，object=个体** | **`object_id`** | **指向目标个体的主语个体（本文主用例：量纲→单位）** | ✓ |
| 62 数据属性断言 | subject=个体，object=属性实体，value_text=字面量 | `object_id` | 用该数据属性断言的个体 + 字面量 | ✓ |
| 100 注解断言 | subject=被注解实体，object_id=注解属性实体（双轨之一）/ predicate_iri=IRI | `object_id`（object_id 轨） | 用该注解属性注解了谁的实体 + 值 | ✓（仅 object_id 轨可反查；IRI 轨谓词侧需显式 predicateIri，V1 不做） |

规则细化：

- **成对公理去重**（21/22/34/35/36/44/45）：存储是 `(A,B)+(B,A)` 两行，反查结果按无序对 `{subject, object}` 去重，保留 `axiom_id` 较小者，并在响应中标记 `paired=true`（前端可关闭"显示成对重复"）。
- **37 属性链**：不能走 `object_id`（成员在 `value_text` JSON 内）。复用 `ontology.ChainReferrers(ctx, allAxioms, propertyID, log)`（对象属性 `Usage` 已有实现），一期在服务层合并结果；二期可考虑把链成员拆表（不做，见 §12）。
- **62 的谓词过滤**：`predicateIri` 解析为数据属性实体后按 `object_id` 匹配（62 的谓词就是 `object_id`）。
- **61 的谓词过滤**：按 `predicate_iri` 字符串精确匹配（属性 IRI 由 `baseIri+localName` 决定，导入保真 IRI 也成立）。
- **100 的"宾语"**：注解断言的宾语是字面量，`ReferenceEdge.object` 为空、`literal_value` 有值（与 62 同构）。

### 3.3 索引现状与查询计划（一期）

沿用既有三索引；主查询：

```sql
SELECT * FROM ont_axioms
WHERE ontology_id = $1 AND object_id = $2 AND deleted_at IS NULL
  AND ($3::bigint[] IS NULL OR axiom_type = ANY($3))
ORDER BY id
LIMIT $4 OFFSET $5;
```

- 计划走 `idx_ont_axioms_object`（§1.1 实测），`axiom_type`/`deleted_at` 为索引内过滤；目标实体局部边数很少，一期规模（数百条）无性能问题。
- 计数查询同条件 `COUNT(*)`，与分页同事务快照读即可（只读，无需事务）。
- 目标实体是类且 `includeDescendants=true` 时，先用 `ontology.SubtreeIDs` 展开类集合再 `object_id = ANY(classIDs)`（复用现有 60 反查路径，树规模有限）。

### 3.4 二期索引迁移草案（按需，未落地）

适用条件：61 边规模 ≥ 数万且"按属性反查"成为高频（如测点/测值建模后）。变更按铁律 6 五步执行：

1. Ent schema `ont_axioms` 增加复合索引定义 `(ontology_id, axiom_type, predicate_iri)`；
2. 新增 goose 迁移 `00006_ontology_axioms_predicate_index.sql`（同一 commit）：

   ```sql
   -- +goose Up
   CREATE INDEX IF NOT EXISTS idx_ont_axioms_predicate
       ON ont_axioms (ontology_id, axiom_type, predicate_iri)
       WHERE deleted_at IS NULL;
   -- +goose Down
   DROP INDEX IF EXISTS idx_ont_axioms_predicate;
   ```

3. `cmd/migrate baseline` 对存量老库纳管（已基线化的库直接 `up`）；
4. CI 漂移守卫 `make db-drift-check` 校验迁移链与 Ent schema 一致；
5. 全员重启后确认 goose 版本 +1。

注意：部分索引（`WHERE deleted_at IS NULL`）需 Ent schema 的 `Indexes` 表达能力核对（Ent 支持 `IndexAnnotation`/谓词有限），若 Ent 侧无法表达谓词，则退化为普通复合索引并在设计记录注明差异。

### 3.5 错误码口径（V1 零新增）

| 场景 | 现成 reason | HTTP |
|---|---|---|
| ontology_id 缺省/为 0、target_id 缺省、分页越界 | `ErrorBadRequest` | 400 |
| 本体不存在或已禁用（复用 `requireOntology`） | 现有本体闸门 reason | 404/403 按既有 |
| 目标实体不存在/已软删/不属于该本体 | `ENTITY_NOT_FOUND` | 404 |
| `axiomTypes` 含未知号段 | `ErrorBadRequest`（附非法值） | 400 |
| `predicateIri` 非绝对 IRI 或与 61/62 以外类型同用 | `ErrorBadRequest` | 400 |

如未来需要前端分流"目标实体不存在"以外的新语义（如"该类型不支持反查"），按 01 号文档号段纪律启用 90~96 段并在 §10 回填。

### 4.2 请求校验顺序（与既有服务一致）

1. `ontology_id` 存在且启用：复用 `requireOntology`（各服务已抽好的同款闸门，新服务内联一份或抽公共函数）；
2. `target_id` 存在、未软删、`ontology_id` 与本请求一致（跨本体目标直接 404，不泄漏他本体实体存在性）；
3. `axiom_types`：逐个校验∈已启用号段全集（`ontology.AllAxiomTypes`），非法即 400；缺省取 §3.2 默认集；
4. `predicate_iri`：非空时校验为绝对 IRI；谓词收敛只对 61/62 有意义——**实现修订 #4**：设计原定"与 61/62 以外类型同用 → 400"，但面板默认集含 100/30 等号段，400 会让"按谓词过滤"在最常见入口直接不可用；改为有效号段收敛到 `{61,62}`（其余号段无谓词语义，自然 0 条），不报错。100 的 IRI 轨谓词侧 V1 不做（§3.2）；
5. `positions`：缺省 `[REFERENCE_POSITION_OBJECT]`；显式含 `REFERENCE_POSITION_PREDICATE` 时目标实体须为对象属性（其余类型直接 0 条，不报错——"没有人把这个实体当谓词用"是合法答案）；含 `REFERENCE_POSITION_CHAIN_MEMBER` 时同理仅对象属性有意义，且谓词收敛开启时链行整体跳过（实现修订 #5）；
6. `page`/`page_size` 钳制：`page ≥ 1`、`1 ≤ page_size ≤ 200`，缺省 1/20（对齐 `docs/list_query_rule.md` 与 `TABLE.DEFAULT_PAGE_SIZE`）；
7. `order_by`：JSON 数组字符串，允许列 `id` / `updated_at`（默认 `["-id"]`，边是流水语义，稳定分页优先于时间序）。

### 4.3 查询与组装管线（两段式，避免 N+1）

```
edgesPage, total  ← 第一段：按 position 分别取边并合并
                   · OBJECT：object_id = target 直查（61/62/60/20/... 全部类型）
                   · PREDICATE：predicate_iri = target.iri 直查（仅 61；100-IRI 轨 V1 不做）
                   · CHAIN_MEMBER：ChainReferrers 内存匹配（仅 37）
                   · 成对类型按无序对去重 → 统一按 id 排序 → 内存分页
nodeIDs           ← 第二段：收集需要展示的实体 id（subject 实体、61 的谓词需按 IRI 反解、
                   62 的数据属性即 object_id、类的子类/父类等）
briefs            ← entityRepo.GetEntitiesByIDs 批量取 brief（id/localName/displayLabel/
                   entityType/iri/deprecated），拼装 ReferenceEdge
```

细节：

- **谓词反解**（61）：同一次请求内把命中的 `predicate_iri` 去重 → 按 IRI 批量查实体（`entityRepo` 已有按 IRI 查询或可用 `ListEntitiesByType`+内存 map；实现时优先单条 `WHERE iri IN (...)`）。反解不到时（理论上 07 期导入已强制声明）降级为 `predicate.localName = IRI 尾段` 且 `resolved=false`。
- **37 合并**：`ListByOntology` 全量读 + `ChainReferrers`；结果进入同一分页序列（一期直接内存分页，属性链行数少；二期若体积增长再考虑落链成员索引表）。
- **去重**：成对类型先取无序对集合（`min(id, max)` 保留小 id），再参与分页，保证 `total` 与 `items` 一致。
- **软删与 deprecated**：`deleted_at IS NULL` 恒过滤；`deprecated` 只标记不隐式过滤（默认展示，`include_deprecated=false` 可关——注意与既有 `Individual.deprecated` 过滤语义对齐：默认不过滤，显式开关）。
- **稳定排序**：`ORDER BY id`（61/62/60 等直查）或合并后按 `id` 排序；分页游标语义与 `list_query_rule` 一致。

### 4.4 `Usage` 与 `ListReferences` 的统一

- 六个 `Usage` 实现改为调用同一数据层 helper：
  - 个体：`axiomTypes=[61]`，按 subject 去重 → 现状完全等价；
  - 对象属性：`axiomTypes=[30,34,35,36]` + 37 链 + `predicateIri=本属性 IRI` 的 61；
  - 类：`ClassUsageAxiomTypes`（含 20/21/22/31/32/41 与 60 实例计数）；
  - 数据/注解/数据类型：各自既有类型集。
- 对外 `EntityUsage` 形状不变；新增回归测试钉死六个 `Usage` 输出（夹具照抄 06 期 `fullScenario()`，注意"个体必须有型"不变量）。
- 好处：删除保护的"引用计数"和浏览的"引用列表"永远同源，不会出现"弹窗说被引用、面板却说没有"。

### 4.5 权限、租户与运维

- 只读端点；权限挂本体建模菜单权限（与个体/类页同级），不做细粒度（沿用现网模式）。
- **新增端点必须打 OpenAPI 并登记 Api 表**：`make openapi` → 重启（读打进二进制的 `assets/openapi.yaml`）→ 管理页「接口同步」全量重建，否则已部署实例租户闸门 403。

## 5. API 契约

### 5.1 proto 草案（领域层，扁平请求体，铁律 3）

```proto
// 引用节点：边的一端（已软删实体不回显；deprecated 仅标记）
message ReferenceNode {
    optional uint32 id = 1 [json_name = "id"];
    optional uint32 entity_type = 2 [json_name = "entityType"];   // 10/20/30/40/50/60（types.go 六类号段）
    optional string local_name = 3 [json_name = "localName"];
    optional string display_label = 4 [json_name = "displayLabel"];
    optional string iri = 5 [json_name = "iri"];
    optional bool deprecated = 6 [json_name = "deprecated"];
    optional bool unresolved = 7 [json_name = "unresolved"];       // 实现修订 #3：61 谓词 IRI 反解失败的标记
}

// 目标实体在行内的位置（反查命中方式；buf lint ENUM_VALUE_PREFIX 要求带枚举名前缀）
enum ReferencePosition {
    REFERENCE_POSITION_UNSPECIFIED = 0;         // 未指定（等价于 OBJECT）
    REFERENCE_POSITION_OBJECT = 1;              // 目标作为宾语（object_id）
    REFERENCE_POSITION_PREDICATE = 2;           // 目标 IRI 作为谓词（predicate_iri；仅 61）
    REFERENCE_POSITION_CHAIN_MEMBER = 3;        // 目标 id 出现在 37 属性链成员 JSON 内
}

// 一条引用边 = 一条未删公理行（成对公理已按无序对去重，paired=true）
message ReferenceEdge {
    optional uint64 axiom_id = 1 [json_name = "axiomId"];
    optional uint32 axiom_type = 2 [json_name = "axiomType"];      // 20/21/22/.../100
    optional uint32 sort_order = 3 [json_name = "sortOrder"];      // 与 DB 列同宽（实现修订 #6）
    optional ReferenceNode subject = 4 [json_name = "subject"];
    optional ReferenceNode predicate = 5 [json_name = "predicate"]; // 61 谓词反解；62/100 为属性实体；其余为空
    optional ReferenceNode object = 6 [json_name = "object"];       // 61/20/34... 的宾语实体
    optional string literal_value = 7 [json_name = "literalValue"]; // 62/100 字面量；42 内建轨 IRI；37 链 JSON
    optional string lang = 8 [json_name = "lang"];
    optional bool paired = 9 [json_name = "paired"];                // 成对公理去重后标记
    optional google.protobuf.Timestamp updated_at = 10 [json_name = "updatedAt"];
    optional ReferencePosition position = 11 [json_name = "position"]; // 本边命中的位置
}

message ListReferencesRequest {
    optional uint32 ontology_id = 1 [json_name = "ontologyId"];
    optional uint32 target_id = 2 [json_name = "targetId"];         // 被反查的实体
    repeated uint32 axiom_types = 3 [json_name = "axiomTypes"];     // 缺省 = §3.2 默认集
    optional string predicate_iri = 4 [json_name = "predicateIri"]; // 仅对 61/62 生效
    optional bool include_descendants = 5 [json_name = "includeDescendants"]; // 仅 60/20（类目标）
    optional bool exclude_deprecated = 6 [json_name = "excludeDeprecated"];   // 实现修订 #2：缺省 false = 只标记不过滤
    optional int32 page = 7 [json_name = "page"];
    optional int32 page_size = 8 [json_name = "pageSize"];
    optional string order_by = 9 [json_name = "orderBy"];
    repeated ReferencePosition positions = 10 [json_name = "positions"]; // 缺省 [REFERENCE_POSITION_OBJECT]
}

message ListReferencesResponse {
    repeated ReferenceEdge edges = 1 [json_name = "edges"];
    optional int64 total = 2 [json_name = "total"];
}

service OntologyReferenceService {
    rpc ListReferences (ListReferencesRequest) returns (ListReferencesResponse) {}
}
```

门面（admin，HTTP 绑定）：

```proto
service OntologyReferenceService {
    rpc ListReferences (ListReferencesRequest) returns (ListReferencesResponse) {
        option (google.api.http) = { get: "/admin/v1/ontology/references" };
    }
}
```

> 请求体为扁平字段（本 RPC 非 CRUD，铁律 3 的正确适用：不包 `{data:{}}`）。GET 的 query 绑定 snake_case/camelCase 均可（既有登录/列表接口同款行为）。

### 5.2 参数语义

| 参数 | 必填 | 语义 | 默认/钳制 |
|---|---|---|---|
| ontologyId | 是 | 本体上下文（跨本体禁止） | — |
| targetId | 是 | 被反查实体（object 侧） | — |
| axiomTypes | 否 | 反查的公理类型子集 | §3.2 默认集（排除 33/43/46/内建 42 轨/100-IRI 轨） |
| predicateIri | 否 | 谓词收敛；61 按 `predicate_iri`、62 按 `object_id`（属性实体） | 只作用于 61/62，其余号段自然 0 条（实现修订 #4） |
| positions | 否 | 目标在行内的位置集合 | `[REFERENCE_POSITION_OBJECT]`；属性抽屉传三值全开 |
| includeDescendants | 否 | 类目标时含子类实例（60）与子类边（20） | false |

## 7. 异常与边界场景清单

| # | 场景 | 预期行为 |
|---|---|---|
| 1 | targetId 指向已软删实体 | 404 `ENTITY_NOT_FOUND`（与既有帧读一致） |
| 2 | targetId 属于他本体 | 404（不泄漏存在性） |
| 3 | axiomTypes 含未启用号段/重复值 | 400，附非法值；重复值去重不报错 |
| 4 | predicateIri 与 axiomTypes 组合非法（如 20 + predicateIri） | 400 |
| 5 | 成对公理（21/22/34/35/36/44/45） | 无序对去重，保留 min(axiom_id)，`paired=true` |
| 6 | 61 谓词实体反解失败（IRI 无对应实体） | 边照常返回，`predicate` 用 IRI 尾段构造、标记未解析（日志 warn） |
| 7 | 37 链成员含已软删属性 | 该成员不出现在链引用结果（成员 id 解析不到实体即跳过并 warn） |
| 8 | 42 内建轨（value_text=内建 IRI） | 默认集不含；显式请求时以"字面量边"返回，`object` 为空 |
| 9 | 100 注解断言的 IRI 轨行 | 目标侧反查不可用（object_id 空）；谓词侧反查 V1 不做 |
| 10 | 同一对实体多条 61 边（不同谓词） | 各为一条边，不合并（这正是与 `Usage` 的差异） |
| 11 | 分页越界 | 空页 + 正确 total |
| 12 | deprecated 端 | 默认展示并标记；不隐式过滤 |
| 13 | 大结果（目标侧边数 > 1000） | 分页承载；`includeDescendants` 的类目标先收敛子树再查（避免类树大导致 IN 列表爆炸） |

## 9. Protégé 对照

Protégé 的 Usage 视图（"Usage" pane）在选中实体后列出**引用该实体的公理（referencing axioms）**，每行是完整公理渲染（如 `PropertyAssertion(hasQuantityKind 摄氏度 温度)`），可按公理类型分组。本设计与其对齐的点：

1. 以"边/公理"为单位而非实体（本设计的 `ReferenceEdge` ≈ 一行 referencing axiom）；
2. 复用 01 号文档 §3.1 的 Manchester 渲染器（`render.go`）即可在面板增加"公理"列，做到与 Protégé 同观感——列为二期可选字段 `rendered`，不影响 V1 契约；
3. 差异：Protégé 的 Usage 视图不提供"按谓词过滤/分页"（规模小），本设计按平台数据量补足；Protégé 反查基于内存公理集，本仓基于索引查询。

## 12. 设计取舍与转译差异记录（本仓自研，无上游对应）

| # | 取舍 | 备选方案 | 结论与理由 |
|---|---|---|---|
| 1 | 边级响应 `ReferenceEdge` | 沿用 `EntityUsageRef`（实体级） | 实体级丢失谓词、无法承载多谓词边；`Usage` 保留原语义仅作删除保护 |
| 2 | 单端点 `OntologyReferenceService` | 六类实体各加 `References` RPC | 端点随实体类型线性增长；参数化幅度更小、契约更稳 |
| 3 | 反查只读、编辑走既有抽屉 | 面板内直接删边 | 写路径已有 `ChangeApplier` 事务管线，重复建设会绕过校验/版本/变更日志 |
| 4 | 37 属性链服务层合并 | 链成员拆表落索引 | 拆表是存储模型变更（重迁历史 + 导出映射改写），收益不匹配当前规模 |
| 5 | 成对公理后端去重 | 返回两行由前端去重 | `total`/分页在服务端才有意义；前端去重会让 total 虚高 |
| 6 | V1 不含内建 42 轨与 100-IRI 轨 | 全量纳管 | 这两类没有"目标实体"可反查（宾语是 IRI 文本），纳管会破坏"边两端都是实体"的模型一致性 |
| 7 | 谓词过滤仅 61/62 | 全类型放开 | 其他类型的"谓词"是宾语关系的语义位而非属性实体，放开只会制造歧义 |
| 8 | 错误码零新增 | 90~96 专属段 | YAGNI：现有 reason 足够前端分流；新增段要动 01 号"定稿"号段表，收益低 |
| 9 | 单端点带 `positions` 三位置 | 拆成 incoming-object / incoming-predicate 两个 RPC | 属性的"被引用"天然跨位置（实测 hasQuantityKind：谓词位 101 条 61 断言、宾语位 30/31/32 若干），拆端点会让同一抽屉调两次且 total 无法合并；`position` 作为边字段还能让 UI 区分来源 |

### 12.1 实现修订（2026-10-23 一期落地记录）

| # | 设计原文 | 实现修订 | 原因 |
|---|---|---|---|
| 1 | 位置枚举 `POSITION_OBJECT` / `_PREDICATE` / `_CHAIN_MEMBER`，`OBJECT=0` | `REFERENCE_POSITION_UNSPECIFIED=0` + `REFERENCE_POSITION_OBJECT=1` / `_PREDICATE=2` / `_CHAIN_MEMBER=3` | buf lint `ENUM_VALUE_PREFIX` + `ENUM_ZERO_VALUE_SUFFIX`；HTTP query 里 UNSIGNED 0 与"未指定"同义，服务层把 0 归一为 OBJECT |
| 2 | `include_deprecated`（缺省 true，"只标记不过滤"） | 改为 `exclude_deprecated`（缺省 false = 不过滤；true 时剔除任一端 deprecated 的边） | proto3/GET query 无法表达"显式 false 覆盖 true 缺省"（生成客户端只在真值时才拼 query），保留原名词会得到一个永远关不掉的开关 |
| 3 | `ReferenceNode` 无"未解析"标记 | 增加 `optional bool unresolved` | §4.3/§7 #6 要求 61 谓词 IRI 反解失败时降级为 IRI 尾段并标记；原 proto 草案漏了承载字段 |
| 4 | `predicateIri` 与 61/62 以外类型同用 → 400 | 允许任意 `axiomTypes`；谓词收敛只作用于 61/62，其余号段自然 0 条 | 面板默认集含 100（个体）/30~37（对象属性）等号段，400 会让最常见入口的"按谓词过滤"直接不可用 |
| 5 | 谓词收敛与 CHAIN_MEMBER 可同时生效（未说明） | 谓词收敛开启时跳过 37 链行 | 链行没有"谓词"字段，保留会造成"过滤后链行仍在"的结果不一致 |
| 6 | `ReferenceEdge.sort_order` 为 `int64` | `uint32`（与 `ont_axioms.sort_order` 列同宽） | 避免无意义的有符号转换；DB 列本就是非负序 |
| 7 | 六类抽屉挂「被引用」**Tab**；面板含"操作"列 | 挂**编辑态抽屉底部的只读区域**；列为主语/谓词/宾语/公理类型/位置/更新时间 | 六抽屉均为 `DrawerForm`，Tab 会与表单提交动线纠缠；只读投影无行操作（§1.4 #4），"操作"列无内容 |
| 8 | "点击节点跳转；一期先支持个体与类，其余禁用" | `openableEntityType + onOpenEntity` 参数化，六类抽屉均支持**同类型**实体跳转；跨类型节点为纯文本 | 页面级只有本类型抽屉的打开入口；给跨类型节点做"禁用态"反而是误导。参数化后零成本覆盖六类 |
| 9 | §4.3"统一按 id 排序 → 内存分页" | 单位置且无成对去重时走 SQL 分页快路径（`orderBy` 首个字段为 id、未开 excludeDeprecated）；其余走内存合并管线 | 谓词位十万级断言时全量进内存不可接受（§4.6）；快路径与合并管线共用同一 repo/投影，输出形状一致 |
| 10 | A9 门禁含 `make lint` | 本机 lint 未能执行：`golangci-lint 2.9.0` 报 export data version 不兼容，对未改动包同样失败 | 环境工具链问题（二进制类型检查器与 Go 1.27 导出格式不匹配），非代码缺陷；已用 `go build ./...` + `go test` + `gofmt` + react typecheck 覆盖可执行门禁 |
| 11 | `make ts` 生成三端 | 仅执行 react 模板（`buf.react.admin.typescript.gen.yaml`） | 铁律 5：vue-element / vue-vben 已冻结，不因本期生成产物改动两端 |
