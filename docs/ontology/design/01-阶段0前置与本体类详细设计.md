## 1. 背景与总体路线

### 1.1 目标

在本仓（backend：Go + Kratos + Ent + PostgreSQL，唯一 Kratos 服务 `app/admin/service`，REST `:7788`；frontend：React 19 + antd 6 + ProComponents + TanStack Query + zustand，`frontend/admin/react`）移植源项目的六项本体建模能力，形成可多用户协作使用的本体建模管理台：

```
阶段0  前置基础设施（实体工厂 / 公理变更事务 / 层级构建 / 结构校验 / 渲染缓存）
01     本体类（OWLClass）          ← 本文
02     对象属性（OWLObjectProperty）
03     数据属性（OWLDataProperty，复用 02 沉淀的属性族抽象）
04     注解属性（OWLAnnotationProperty，注解机制的最简退化子集）
05     数据类型（OWLDatatype，无层级、纯列表）
06     个体对象（OWLNamedIndividual，依赖前五项；身份与赋码）
07     OWL 导入导出（RDF 序列化互操作）
```

**为什么先做类**（沿用源结论）：类是六项中唯一的"骨干实体"——个体按类断型、属性的定义域/值域指向类、类表达式是所有公理的骨架。把通用管线（实体注册 → 公理事务 → 层级构建 → 校验 → 渲染 → 树/列表 UI）在类上打磨成熟，后续五项都是对该管线的增量实例化。

### 1.2 三层同构映射（Protégé → 源 Java 项目 → 本仓）

Protégé 桌面端是"内存 OWLAPI 模型 + 单用户 Swing"；源项目是"PG 事实源 + Spring 事务 + 多用户 Web"；本仓保持源项目的**事实源与事务模型不变**，只替换框架设施：

## 2. 关键架构决策

### 2.1 决策一：admin 服务内新增 ontology 域（双层 proto），**不**建独立 Go module

**结论：在本仓常规模块形态落地**——新增 proto 域 `backend/api/protos/ontology/service/v1/`（源领域，只定义消息与 rpc，无 HTTP 注解）+ admin BFF 门面 `backend/api/protos/admin/service/v1/i_ontology.proto`、`i_ontology_class.proto`（挂 HTTP 注解），service / repo / ent schema 落在 `app/admin/service/internal/` 内。与 dict 模块（`i_dict_type.proto` + `dict_type_service.go` + `api_repo.go`）同款形态。

**不采用** onestop 式独立 Go module（`backend/onestop` + go_package 覆盖 + 双 buf 配置 + `OperatorReader` 注入）的理由：

1. onestop 的独立形态是为"未来可能独立演进的业务域"预留自治权，代价是双 buf 配置、独立 ent client、装配期注入等复杂度；本体建模 V1 无独立部署诉求；
2. 本体域重度复用宿主设施：go-crud 通用仓储、`pagination.PagingRequest` 分页、认证/鉴权/审计/租户闸门中间件链、`auth.FromContext` 操作人提取——常规模块形态下全部零成本可用；
3. 源项目"新建独立 module"的三条理由（域内聚 / 不改上游 / 增量提交）在本仓由"独立 proto 包 + 独立 ent schema 文件 + 独立 service 文件 + 独立域内核包（§3.0）"同样满足，且不引入跨 module 边界。

**升级路径**：proto 双层分离已把领域消息与门面路由解耦，未来若需独立部署，按 `backend/onestop/README.md`「新增实体的步骤」把 `internal/ontology` 域内核 + repo/service 迁出即可，本文不预留多余机制。

### 2.2 决策二：PG 四表为唯一事实源，层级由公理派生，**不用** `mixin.Tree`

与源一致的核心模型：**实体表 + 公理表双表事实源**，层级全部由 `SUBCLASS_OF(20)` 公理派生，树上不做 `parent_id` 冗余。

本仓有一个强先例会诱导走捷径——`mixin.Tree[T]{}`（`parent_id` 自关联 + 服务层环校验，onestop `service_type.go` 即此）。**明确不走**，理由：

1. **多继承**：本体类支持多父类（一个类挂多个父类下），单值 `parent_id` 结构性无法表达；
2. **第二事实源漂移**：`parent_id` 与 `SUBCLASS_OF` 公理会形成两份层级真相；Protégé 的 `AssertedClassHierarchyProvider` 本就是从公理派生层级，源实现验证了该路线；
3. **公理即审计对象**：层级变更必须走公理事务（乐观锁 + 校验 + 变更日志），绕过公理直接改 `parent_id` 会破坏变更日志完整性。

同理，`ont_entities` / `ont_axioms` 之间**不建 FK 约束**（源同款）：跨表一致性由公理事务管线在同一 `ent Tx` 内保证，删除级联由服务层执行（§4.5）。

不采用的其它替代方案（沿用源论证）：整体存 OWL 序列化大字段——无法行级查询（树/分页/usage 反查都要全量解析）、多用户并发无法做乐观锁。

### 2.3 决策三：平台级表——不挂 `mixin.TenantID`、不配租户 Policy

四张 `ont_*` 表均为平台级共享知识资产（建模用户是平台管理员），照 `sys_languages` / `sys_configs` / `onestop_service_types` 先例：Mixin 只取 `AutoIncrementId + TimeAt + OperatorID`（+ 本体文档表的 `IsEnabled`），不挂 `mixin.TenantID[uint32]{}`、不配 `TenantMutationGuardPolicy`。判定标准见 `docs/tenant_isolation.md`：是否平台级看 schema 是否装配 TenantID mixin，本模块四表均不装配。若未来需要租户隔离，扩展点是四表补 TenantID mixin + Policy + 号段迁移，本文不做。

菜单与前端路由的可见性同步收敛为 `sys:platform_admin`（§3.8）。

### 2.4 决策四：本体级乐观锁——`version` + `baseVersion` + `SELECT FOR UPDATE`（本仓首个乐观锁先例）

- `ont_ontologies.version uint32 Default(0)`；任何公理级变更（创建/修改/删除实体）在同一事务内 `version + 1`；
- 变更请求携带 `baseVersion`（从 frame 接口取当前版本回传），事务内先 `SELECT ... FOR UPDATE` 锁定本体行再比对（ent `sql/lock` feature 已在 `backend/app.mk` 启用，`Query().ForUpdate()` 可用），不等 → `ONTOLOGY_VERSION_CONFLICT`（HTTP 409）；
- `baseVersion` 为空 = 跳过版本比对，仅限内部初始化路径（与源修订 #7 同语义）；
- 粒度为本体级而非实体级：与 Protégé `applyChanges`（本体级变更批）语义一致，实现最简；细粒度冲突提示（"谁改了哪个类"）依赖变更日志展示，不阻塞操作。

与源实现的差异（源是应用层读版本比对、无行锁，`SELECT` 与比对之间存在竞态窗口）：本仓在 `FOR UPDATE` 行锁下比对再自增，把窗口彻底关死；这是本仓**第一个乐观锁先例**（现存 `version` 字段均为业务语义，见 `schema/script.go` 热更新指纹），后续模块可参照本节模式。

### 2.5 决策五：纯 Go 结构校验器替代 OWLAPI

源项目引入 `owlapi-distribution 5.5.1` 做保存时编译校验（全量投影为内存 `OWLOntology`，投影过程即校验）。**Go 生态没有可用的 OWL 2 API 等价物**（无维护良好的 OWL 公理/序列化/渲染库），故：

- V1 校验项（§3.6）全部是**结构规则**（IRI 语法、引用存在性、类型匹配、声明完备性、注解谓词合法性），不需要 OWL 推理机，用纯 Go 校验器逐条实现，语义与源 `OntAxiomCompiler` 的 V1 校验集对齐；
- Manchester/OWL 2 渲染字符串（frame 详情的公理描述）由手写渲染器产出（§3.6），V1 不落库、详情接口实时计算；
- 环检测独立于校验器前置执行（§4.3），与源分工一致；
- **收益**：零重依赖（owlapi-distribution 传递依赖极重，源项目专门处理过打包收敛），校验器可单测；
- **代价与去向**：07 期 OWL 导入导出需要 RDF/XML / Turtle 序列化，届时再评估轻量 RDF 库（如 `knakk/rdf`，仅覆盖 Turtle/N-Triples）或自写序列化器，由 07 号文档定案，本文不预引入。

## 3. 阶段0：前置基础设施详细设计

### 3.0 域内核包：`internal/ontology`

本仓无 `biz/` 层（biz 职责折叠进 data/service），但本体域的工厂/事务/层级/校验逻辑既不属于 HTTP service 也不属于 repo。为避免六个功能期把 service 文件撑成巨石，新增**域内核包**：

```
backend/app/admin/service/internal/ontology/     # 本体域内核（非 HTTP、非仓储；纯 Go 可单测）
├── types.go          # OntEntityType / OntAxiomType 常量（与 proto 枚举数值一致）+ 内建谓词 IRI 常量
├── entity_factory.go # EntityFactory：IRI 构建、localName 校验、查重、引用实体校验
├── changeset.go      # AxiomChange / EntityChangeSet + 四组 diff 算法（§4.4）
├── applier.go        # ChangeApplier：公理事务管线七步（§3.4）
├── hierarchy.go      # HierarchyBuilder：树构建 / nav 剪枝 / 子树闭包 / 环检测（§3.5 / §4.3）
├── validator.go      # AxiomValidator：纯 Go 结构校验（§3.6）
└── render.go         # Manchester 子集渲染器（§3.6）
```

依赖方向：`internal/ontology` 只依赖 ent 生成类型与标准库（仓储需求以小接口注入，如 `EntityReader` / `AxiomReader`，便于单测桩替换）；`internal/data`（repo）与 `internal/service`（HTTP 编排）依赖它，反向禁止。02~06 期全部在此包内增量扩展。

|---|---|---|

#### 3.1.2 Ent schema（`internal/data/ent/schema/`，四个文件）

**`ont_ontology.go`（type `OntOntology`）**——其余三表 Mixin 同款（`AutoIncrementId + TimeAt + OperatorID`）：

```go
func (OntOntology) Annotations() []schema.Annotation {
    return []schema.Annotation{
        entsql.Annotation{Table: "ont_ontologies"},
        entsql.WithComments(true),
        schema.Comment("本体文档表（owl:Ontology，平台级：不挂 TenantID、不配租户 Policy，参照 sys_languages）"),
    }
}

func (OntOntology) Mixin() []ent.Mixin {
    return []ent.Mixin{mixin.AutoIncrementId{}, mixin.TimeAt{}, mixin.OperatorID{}, mixin.IsEnabled{}}
}

func (OntOntology) Fields() []ent.Field {
    return []ent.Field{
        field.String("ontology_name").Comment("显示名").MaxLen(128).NotEmpty().Optional().Nillable(),
        field.String("ontology_iri").Comment("本体 IRI（owl:Ontology IRI，全局唯一）").MaxLen(512).NotEmpty().Optional().Nillable(),
        field.String("base_iri").Comment("实体命名空间，以 # 结尾；实体 IRI = base_iri || local_name").MaxLen(512).NotEmpty().Optional().Nillable(),
        field.String("description").Comment("描述").MaxLen(512).Default("").Optional().Nillable(),
        // 乐观锁版本号：任何公理级变更事务内 +1（本仓首个乐观锁先例，见设计文档 §2.4）
        field.Uint32("version").Comment("乐观锁版本号").Default(0).Optional().Nillable(),
    }
}

func (OntOntology) Indexes() []ent.Index {
    return []ent.Index{
        index.Fields("ontology_name").StorageKey("idx_ont_ontologies_ontology_name"),
        index.Fields("ontology_iri").Unique().StorageKey("uix_ont_ontologies_iri").
            Annotations(entsql.IndexWhere("deleted_at IS NULL")), // 软删后 IRI 可复用
    }
}
```

**`ont_entity.go`（type `OntEntity`）**：

### 3.2 本体文档管理（OntologyService）

**形态：标准通用 CRUD**（go-crud 泛型仓储 `entCrud.NewRepository`，镜像 dict_type 全链路），加一个自定义 RPC `simple-list`：

- 标准 CRUD：分页 List（`pagination.PagingRequest`，名称走 `ontologyName__contains` 模糊，铁律 3）/ Get / Create / Update（`updateMask`）/ Delete（支持批量）；
- `base_iri` 校验：必须为合法绝对 IRI（`net/url.Parse` 成功且含 scheme），尾部无 `#` 时统一补 `#`；错误 `ONTOLOGY_BASE_IRI_INVALID`；
- `base_iri` **创建后不可变**（Update 服务层忽略该字段，前端编辑态禁用输入——源修订 #1：变更命名空间会使既有实体 IRI 语义漂移）；
- `ontology_iri` 全局唯一（partial unique index 兜底 + 前置校验友好报错）；同名本体服务层查重拒绝（`ONTOLOGY_NAME_DUPLICATE`，沿用源语义；名称唯一性不建索引，允许删除后重建同名）；
- 删除本体：同一事务级联软删该本体下 `ont_entities` / `ont_axioms` / `ont_change_logs` 全部行（变更日志随本体消亡，跨本体的操作审计由宿主审计日志中间件承载）；前端二次确认弹窗固定警示"将同时删除该本体下全部实体与公理"。V1 不做"本体引用本体"（owl:imports）；
- **活动本体概念**：不设服务端会话状态。活动本体 = 前端 zustand 全局上下文（§3.9），所有实体级 API 显式携带 `ontologyId`（或由实体 id 反查），服务端无状态、天然支持多标签页；
- **启动期播种**（实现期补充）：`ont_ontologies` 空表时由 `OntologyService.init()` 落内置种子本体**"有名万物"**（`constants.DefaultOntologies`，本体 IRI 与实体命名空间同为 `https://youmingwanwu.com/ontology/youmingwanwu#`，count==0 守卫与 `DefaultLanguages` 同机制；老库删除该本体后重启会重新播种，partial unique index 排除软删行故无唯一冲突）。

### 3.4 公理变更事务（EntityChangeSet + ChangeApplier，对应 `applyChanges`）

`internal/ontology/changeset.go` + `applier.go`：

```go
type AxiomOp string // "ADD" | "DELETE"

type AxiomChange struct {
    Op           AxiomOp
    AxiomID      uint32 // DELETE 时必填；ADD 时零值
    AxiomType    uint32 // ADD 时必填（OntAxiomType 常量）
    SubjectID    uint32
    ObjectID     uint32 // 可零值
    PredicateIRI string
    ValueText    string
    Lang         string
    SortOrder    int32
    // 引用本次新建实体（实现期修订 §8.1 #20，零值安全约定）：
    // 0 = 无引用（直接用 SubjectID/ObjectID）；N = 该端取 NewEntities[N-1] 落库后的真实 id。
    // 零值必须是"无引用"——否则字面量构造漏置哨兵时会把公理错绑到新实体自身（e2e 实测踩中过）。
    SubjectNewEntityRef int
    ObjectNewEntityRef  int
}

// 待创建实体草稿（create 路径新实体尚无自增 id，与公理变更的草稿引用配对使用）
type EntityDraft struct {
    EntityType uint32
    IRI        string
    LocalName  string
}

// 一次保存 = 一组公理级增删；由各功能服务（01 类 / 02 属性 ...）组装，Applier 统一执行
type EntityChangeSet struct {
    OntologyID  uint32
    BaseVersion *uint32        // nil = 跳过版本比对（仅限内部初始化路径）
    Operation   string         // 落 ont_change_logs.operation：CREATE_CLASS / UPDATE_CLASS / ...
    NewEntities []EntityDraft  // 本次新建实体草稿（Changes 以 NewEntityRef 引用其落库后 id）
    Changes     []AxiomChange
    // 级联软删的实体（force 删除路径）：实体行随公理一并消亡（实现期补充，源 OWLEntityDeleter 语义）
    DeleteEntityIDs []uint32
}
```

事务管线（`ChangeApplier.Apply(ctx, set)`，`entClient.Tx(ctx)` 包裹，任何一步出错 `Rollback`）：

1. 本体行 `SELECT ... FOR UPDATE`（`ForUpdate()`）；本体不存在（含已停用/已删，文案区分）→ `ONTOLOGY_NOT_FOUND`；
2. `BaseVersion` 非 nil 且 ≠ 行内 `version` → `ONTOLOGY_VERSION_CONFLICT`（409）；
3. 逐条应用变更：先落库 `NewEntities`（取得自增 id，登记草稿下标 → id 映射），再逐条应用 `AxiomChange`：ADD → `ont_axioms` 插入（`created_by` 取 `auth.FromContext`，系统上下文取 0）；DELETE → 软删（置 `deleted_at` / `deleted_by`）；最后软删 `DeleteEntityIDs`（force 删除路径，实现期补充）；
4. 注解缓存同步：收集本次变更全部 `subject_id` 去重，按 §3.3 规则重算并更新 `ont_entities.display_label / deprecated`（已软删实体跳过）；
5. `AxiomValidator.Validate(ontologyID)`（§3.6，事务内读全量未删实体 + 公理做结构校验）失败 → 整体回滚；
6. `ont_ontologies.version + 1`；
7. 写 `ont_change_logs`（operation + JSON 快照（元素为公理字段对象）+ before/after_version）。

返回：新实体 id 列表 + 变更后版本号（前端创建后选中新节点，对应 Protégé `setSelectedOWLObject(newClass)`）。

### 3.6 编译校验器（AxiomValidator）与 Manchester 渲染

**校验器**（`validator.go`，替代源 `OntAxiomCompiler` 的 OWLAPI 投影，见决策五）。输入：ontologyID（事务内读取）；V1 校验项：

1. **IRI 语法**：每实体 `iri` 可被 `url.Parse` 解析为绝对 IRI 且以本体 `base_iri` 为前缀；
2. **引用存在性与类型匹配**：每条公理的 `subject_id` / `object_id`（非零时）都指向**同本体、未删、类型匹配**的实体——`SUBCLASS_OF(20)` / `DISJOINT_WITH(21)` / `EQUIVALENT_CLASSES(22)` 两端均须为 `CLASS(10)`；
3. **声明完备性**：每实体恰有一条未删 `DECLARATION(10)` 公理，反之每条 10 型公理主体存在（软删实体时由删除流程保证同步，此处为防御校验）；
4. **注解断言双轨**：`ANNOTATION_ASSERTION(100)` 的谓词必须命中内建谓词白名单（`rdfs:label` / `rdfs:comment` / `owl:deprecated` / `skos:notation`，常量定义在 `types.go`）或 `object_id` 指向注解属性实体（04 期激活，本期白名单外一律拒绝）；`lang` ≤ 16 字符；
5. **值词法**：`owl:deprecated` 值域 `"true"` / `"false"`；`skos:notation` 字符集 `[A-Za-z0-9_\-]+`（编码语义与取号机制见 06 号文档，本期仅手工录入 + 校验）；
6. 层级无环：环检测在写路径前置执行（§4.3），校验器**不重复**（职责分工，与源一致——源也是编译器外独立 `assertNoCycle`）。

### 4.1 功能范围

- 复杂类表达式父类（`some/all/not/and/or`）→ 依赖 02/03 属性，02 期后开放（`ont_axioms.value_text` 列已预留表达式 JSON 落点，等价/父类公理升级路径不变）；

### 4.2 数据模型落点

- `ont_entities`：`entity_type = 10 (CLASS)`；
- `ont_axioms` 本期用到：`DECLARATION(10)`、`SUBCLASS_OF(20)`（subject=子类，object_id=父类实体 id，多父多条按 `sort_order` 保序）、`DISJOINT_WITH(21)` 与 `EQUIVALENT_CLASSES(22)`（**成对存储**：(A,B) 与 (B,A) 各一行——OWL n-ary 在序列化期可合并，成对存储让 usage 反查与差异计算均为 O(1) 行操作，与源一致）、`ANNOTATION_ASSERTION(100)`（subject=类，predicate_iri = rdfs:label / rdfs:comment / owl:deprecated / skos:notation，value_text=值；label/comment 带 `lang="zh"`，deprecated/notation 无 lang）。

### 4.3 类层级构建算法（HierarchyBuilder，对应 `AssertedClassHierarchyProvider`）

```
输入: ontologyId
1. entities = ont_entities WHERE ontology_id=? AND entity_type=10 AND 未删
2. edges    = ont_axioms WHERE ontology_id=? AND axiom_type=20 AND 未删
             且 object_id ∈ declared(entities)     // 指向未声明/外部实体的边不参与建树（仍可过校验）
3. childMap = edges GROUP BY object_id             // 父 -> 子列表，按 sort_order, display_label 排序
4. roots    = entities 中无入边者（childMap 中无人指向它）
5. 虚拟根   = owl:Thing（固定 IRI，不入库）：服务端返回根列表，Thing 节点由前端固定渲染
             （不可编辑删除，仅可"新建子类"——源修订 #5：虚拟根属于渲染关注点）
6. 防御环   : 递归构建时携带 path 集合，理论已禁止成环；脏数据出现环则跳过该边并 WARN 日志
输出: OntologyClassTreeNode { id, iri, localName, displayLabel, deprecated, childCount, children[] }
```

**骨架树（nav-tree，源修订 #15 内化为 V1 必做）**：业务类随建模推进可达万级，全量树既是 payload 也是导航噪音。`NavTree` 在全量树基础上剪枝：

```
keepInNav(node, depth) = depth <= NAV_KEEP_DEPTH || node.childCount > 0   // NAV_KEEP_DEPTH = 2
// 1=根类、2=域入口，该深度内无条件保留；更深的"有父类且无子类"叶子剪掉（域入口本身可能是叶子，如工种/计量单位，故按深度无条件保留）
// 实现期修订（§8.1 #21）：保留判定用 childCount（剪枝前的真实直接子类数），不能用剪枝后的
// len(children)——后者会把"有真实子类的深层分支"整枝折叠（子叶子被剪 → 分支 children 变空 →
// 分支自己也被剪），违背"深层有子节点是导航入口"与验收 #7"叶子下新建类后升格进骨架树"
// 节点带 childCount（真实直接子类数），被剪叶子体现为 childCount 与 len(children) 的差值
```

左树默认用骨架树；勾选"全部类"或打开表单（父类/不相交/等价选择器）时才按需拉全量树（`tree` 接口语义不变）。骨架视图搜索无命中时提示"叶子类不在树中，请切全部类查找"。antd `Tree` 支持 `height` 虚拟滚动，作为全量树渲染性能的**补充防御**（源 el-tree 无虚拟滚动是其硬约束，本仓树规模防御双保险：骨架化为主、虚拟滚动为辅）。

**子树闭包**（分页"仅看子树"用）：`SubtreeIDs(rootID)` 迭代 DFS 沿 20 型边收集后代闭包（含自身，visited 去重防脏环）——服务端计算，前端只传 `rootId` 一个参数，不传整串 id。

**环检测**（写路径前置校验，独立于校验器）：

```
addParents(X, newParents):
  构建 子->父 邻接表（当前未删 20 型边 + 本次新增）
  从每个新父沿父链向上走（栈式，记录 originParentID 供报错定位）
  回到 X → 拒绝 HIERARCHY_CYCLIC（自环 X→X 同样被捕获）
```

#### 4.4.2 事务与校验顺序（create / update 共用管线）

1. 本体存在且启用 → 2. localName 合法（create）→ 3. IRI 查重（create，双层 §3.3）→ 4. `ValidateRefEntities`：parentIds / disjointIds / equivalentId 均为本体下**已声明的类**且 ≠ 自身（update 时；create 不做自引用校验——新实体无 id）→ 5. `AssertNoCycle`（§4.3，全量新父集）→ 6. 组装 `EntityChangeSet`（update 先做 frame diff，见下）→ 7. `ChangeApplier.Apply()`（§3.4 全流程）。

update 时 `local_name` **忽略**（不参与 diff、不校验，与源语义一致——局部名不可变由"不生成任何触及它的公理变更"保证，前端编辑态禁用输入；`base_iri` 同款处理见 §3.2）。

**update 差异计算**（frame 全量提交语义，`changeset.go` 四组 diff）：

- `DiffSubjectSideRelations`（单边关系：父类）：当前 20 型公理 object 集合 vs 目标集合，删旧增新，按提交顺序重写 `sort_order`；
- `DiffSymmetricPairs`（对称关系：不相交）：伙伴集 = 以我为主语的宾语 ∪ 以我为宾语的主语，删/增均**成对两行**；
- `DiffAnnotations`（内建注解）：label / comment / notation 三谓词逐个 replace——值相等跳过，删旧行 + 加新行；**字段缺省 = 不变、提交空串 = 清空该注解**（实现期修订 §8.1 #19：protojson 对 optional 字段的 JSON null 不置 presence，"null"与"缺省"不可区分，不可用 null 表达清空）；`deprecated=false` = 移除 owl:deprecated 断言（源修订 #8 全量替换语义）；
- 等价（22 型）：单值 diff，同样成对；提交 `equivalent_id=0` = 清空，缺省 = 不变。

### 4.5 删除保护与 Usage（对应 `OWLClassUsageViewComponent` + `OWLEntityDeleter`）

- `usage(id)`：反查 `ont_axioms WHERE ontology_id=? AND object_id=? AND axiom_type IN (20,21,22) AND 未删`，按 `axiom_type` 分组返回引用方实体（id / local_name / display_label / axiom_type）。**引用集初值 {20, 21, 22}**（`internal/ontology` 内定义为常量切片 `ClassUsageAxiomTypes`）；02 期对象属性定义域/值域（31/32）、03 期数据属性定义域（41）、06 期个体断型（60）落地时各自往切片加号段（源修订 #12/#14 的缺口已在本仓前置内化，各期文档落地时执行）；
- `delete` 语义（安全优先 + Protégé 级联兜底）：
  - `force=false`（默认）：存在引用 → `ENTITY_IN_USE`（409），错误信息带数量，前端拉 usage 明细弹窗展示，用户先去解除引用；
  - `force=true`：级联软删**以该实体为宾语的引用公理行**（等价 `OWLEntityDeleter` 语义），随后软删实体行、其 DECLARATION、主语侧全部公理与注解；子类自动变根类（其 20 型边被清）；前端二次确认（红字"将同时移除 N 处引用"）；
  - 两路径同一事务、同一乐观锁、同一变更日志（`DELETE_CLASS`）。

### 4.7 异常与边界场景清单

| # | 场景 | 行为 |
|---|---|---|
| 1 | IRI 重复（同名实体） | 前置校验 `ENTITY_IRI_DUPLICATE`（表单局部名红字）；并发双写由 partial unique index 兜底（`23505` → 同 reason） |
| 2 | 环：把子孙设为父类 | `HIERARCHY_CYCLIC`，message 指明"X 已是 Y 的祖先" |
| 3 | 乐观锁冲突 | `ONTOLOGY_VERSION_CONFLICT`（409），引导刷新重试 |
| 4 | 删除被引用类（force=false） | `ENTITY_IN_USE` + usage 明细弹窗 |
| 5 | 删除有子类的类 | 子类引用父类即引用，同 4 拒绝；force=true 则子类自动变根类 |
| 6 | parentIds / disjointIds / equivalentId 含已删/未声明/跨本体实体 | `ENTITY_TYPE_MISMATCH`，message 带具体 id |
| 7 | 并发创建同名 | partial unique index 硬兜底（优于源"接受双写"方案，§3.1.3） |
| 8 | 树脏数据成环（历史/手工改库） | 构建器防御跳过该边 + WARN（§4.3 第 6 步） |
| 9 | 本体被停用 | 实体级接口一律拒绝（`ONTOLOGY_NOT_FOUND` 文案区分"已停用"，不另设 reason——沿用源处理） |
| 10 | display_label 缓存与公理漂移 | 仅服务层写路径会改公理，直改库属运维操作；发现漂移以公理为准（下次编辑同步刷新） |
| 11 | 误按 CRUD 惯例给类接口包 `{ data }` | protojson 丢弃未知字段，接口 200 字段全空——hooks 层已按扁平封装，code review 检查点（铁律 3 陷阱） |
| 12 | 本体文档 Update 试图改 base_iri | 服务层忽略该字段（不报错、不生效），前端编辑态禁用输入 |

## 8. 与源设计的转译差异记录

源项目（Java）语义向本仓（Go）转译时**有意偏离**源实现的决策，逐条记录（实现与后续 02~07 期文档均以本表为准；未列出之处语义与源一致）：| # | 主题 | 源项目 | 本仓定案 | 理由 |
|---|---|---|---|---|
| 1 | 编译校验引擎 | owlapi-distribution 5.5.1 全量投影 | 纯 Go `AxiomValidator` 结构校验 + 手写 Manchester 渲染 | Go 无 OWL API；V1 校验项均为结构规则；零重依赖；07 期再定 RDF 序列化方案 |
| 2 | DDL 通道 | Flyway `V20261014_02`（含菜单 SQL 种子） | goose `00003_ontology_module.sql`（纯 DDL）；菜单走 Go 侧 `default_data.go` 播种 | 铁律 6 + 本仓种子机制；菜单不进 SQL |
| 3 | 单测基建 | H2 内存库（MySQL 模式）15 用例 | 域内核纯函数/接口桩单测 + 本地 PG 端到端验收 | 铁律 4 禁 sqlite/内存库；域内核按可测性设计 |
| 4 | 乐观锁实现 | 应用层读版本比对（无行锁，存在竞态窗口） | `SELECT ... FOR UPDATE` + 比对 + 自增（ent `sql/lock` 已启用） | 关死竞态窗口；本仓首个乐观锁先例 |
| 5 | IRI 唯一性 | 服务层查重 + 接受并发双写兜底 | 前置查重 + partial unique index `(ontology_id, iri) WHERE deleted_at IS NULL`，`23505` 映射 `ENTITY_IRI_DUPLICATE` | 本仓本有唯一索引惯例；PG 部分索引恰好给出软删复用语义 |

### 8.1 实现期修订记录（2026-10-22 实现落定，效力同正文）

| # | 主题 | 正文原设计 | 实现定案 | 理由 |
|---|---|---|---|---|
| 19 | 注解"提交 null = 清空" | §4.4.2：提交 null 清空该注解 | **空串 = 清空、字段缺省 = 不变** | protojson 实测（protobuf-go）对 optional 字段的 JSON null 不置 presence，"null"与"缺省"不可区分；`deprecated` 的 false 移除断言语义不受影响（bool 有值即置 presence）。前端 ClassDrawer 按此封装 |
| 20 | 新实体引用编码 | §3.4：AxiomChange 以草稿下标引用未落库实体 | 定为**零值安全约定**：`0 = 无引用`、`N = 引用 NewEntities[N-1]` | 字面量构造漏置哨兵时零值会被误解析成"引用草稿 0"（端到端冒烟实测踩中：父类公理 object 错绑为新实体自身）；零值=无引用使构造方默认正确 |

| 22 | 软删实现 | §3.1.1：`deleted_at timestamptz`（TimeAt mixin 软删） | **显式软删**：删除一律 UPDATE 置 deleted_at/deleted_by，全部读路径显式 `DeletedAtIsNil` 过滤 | 本仓 go-crud `TimeAt` mixin 只加列、不带 SoftDelete 拦截器（现有各表实际为硬删惯例）；本体模块按设计要软删，只能显式实现并逐查询过滤，不引入全仓拦截器 |
| 23 | 老库菜单 id | §3.8：菜单 110~112 落库 | 固定 id 仅**全新库**由 count==0 播种落库；已部署老库走管理页「菜单同步」(MERGE)——前端推送路由树**不带 id**，按全路径合并落自动 id，另需「权限管理」勾选 | 与 `menu_repo.SyncMenus` 的既有语义一致（前端 routeToMenu 不携带 id）；e2e 冒烟已验证 MERGE 合并 |

| 25 | 树根排序 | §4.3 第 3 步仅约束父内子列表排序 | 根列表同规则**确定性排序**（display_label → id） | 服务端无序返回会让左树根顺序抖动；子列表排序语义推广到根 |
