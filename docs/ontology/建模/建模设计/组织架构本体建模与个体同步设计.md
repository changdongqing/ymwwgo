## 0. 结论摘要（V1.1 范围）

1. **本期核心两件事**：① 落组织架构本体 TBox（类/属性/公理/注解，不落个体）；② 组织类型字段与本体类做**表单展示关联**（下拉 value 仍是现有 `type` 枚举，label 附带本体类名；不做级联、不落类 ID、不加字段）。AI 同步契约作为后续设计，建议本期先写最小版（映射配置/runbook），但不是硬交付，也不实现同步。
2. **本期零表结构、零扩展字段、零同步实现**：不新增 `sys_org_units` 列/子表/JSONB，不新增同步映射表，不写同步 worker，不跑组织个体回填。
3. **本期不改组织类型枚举**：不补 `GROUP`/`STORE`，不修 `SUBSIDIARY`/`BRANCH`；Ent 侧现有 8 个值原样使用，前端 `SUBSIDIARY`/`BRANCH` 仍为“可选但不可保存”的已知问题。`Group`/`Store` 类先建但暂无实例；后续若要落 Group/Store，再单独做“代码级枚举对齐”（不涉及表结构）。
4. **TBox 仍按“域根 + 抽象层 + 类型类 + 职能/业态子类”建全**：`NamedThing → OrgElement → OrgUnit → 集团/区域/法人单位/门店/项目/部门/事业部/委员会/团队/其他`；`Person → User`、`Position` 与 `OrgUnit` 平级挂在 `OrgElement` 下。业态/职能叶子类先作为预留词表，本期不要求有实例。
5. **展示关联采用 A 方案**：例如下拉显示“门店（Store）”“法人单位（LegalEntity）”；提交值仍是 `STORE`/`COMPANY`，编辑回显、列表筛选、存量数据都不变。**不是**把选项换成类，也**不是** `type → 类` 的级联选择。
6. **AI 同步可以不做自定义 worker，但不能没有契约**：后续至少需要机器可读的 `type → 类`/`字段 → 属性` 映射、稳定编码 `T{tenantId}-ORG-{orgId}`、来源注解、写入工具、校验与孤儿策略。AI 只调现有个体 API/域内核，不直接写 `ont_*` 表。
7. **本期明确延后**：`subtype`、17 个扩展字段、动态表单、枚举新增、组织个体同步、人员/职位同步。原 V1.0 的详细设计保留为后续阶段参考，不作为本期交付。

## 1. 背景、目标与非目标

### 1.1 业务背景

百货商场/购物中心运营集团的组织结构通常有两套同时存在的维度：

- **管理归属树**：集团 → 区域 → 城市公司/项目公司 → 购物中心/百货门店 → 部门 → 团队；
- **法律/经营主体维度**：门店可能由某个项目公司持有或受托经营，区域公司本身也可能是独立法人；分公司不是独立法人，但仍是登记经营主体。

现有 `sys_org_units` 已经同时提供 `parent_id`（管理树）与 `legal_entity_org_id`（法人归属）两个维度，方向是对的；但 `type` 枚举只有 8 个值，既没有“集团”“门店”，前端可选的“子公司/分公司”后端又不认，无法承载上述组织形态。

### 1.2 目标（V1.1）

1. 在“有名万物”本体中建立组织域 TBox：覆盖集团、区域、法人单位、门店（含百货/购物中心/社区商业/奥莱）、项目、部门（含招商/营运等职能）、事业部、委员会、团队、其他组织，以及 `Person`/`User`/`Position` 配套类。
2. 在组织架构表单里把现有 `type` 枚举与本体类做**展示关联**：`value` 不变，`label` 附带本体类名；不做级联、不落库、不加字段。
3. 定义 AI 同步的最小契约：`type → 类`、`字段 → 属性`、稳定编码、来源注解、写入工具、校验、孤儿策略、dry-run runbook；作为后续设计，本期不实现（建议先写最小版）。
4. 明确后续扩展（`subtype`/扩展字段/枚举对齐/同步/人员职位）的边界与触发条件，避免本期范围回潮。

### 1.3 非目标（本期明确不做）

| # | 不做项 | 理由/去向 |
|---|---|---|
| 1 | 新增 `sys_org_units` 扩展字段/子表/JSONB | 评审后收敛；17 个字段与动态表单保留为后续方案 |
| 2 | 修改组织类型枚举（补 `GROUP`/`STORE`、修 `SUBSIDIARY`/`BRANCH`） | 本期不动组织模块代码；Group/Store 类先预留。后续如要落实例，再单独做代码级枚举对齐 |
| 3 | 组织个体同步（worker/映射表/回填/只读保护） | 后续由 AI 驱动；本期只写契约与 runbook |
| 4 | `type → 类` 级联选择、类 ID 落库 | 级联第二级需要 `subtype`/`class_id` 字段；本期不加字段 |
| 5 | 人员/职位/任职关系同步 | 后续 AI 同步阶段；本期只建 `Person`/`User`/`Position` 类 |
| 6 | 本体个体页面直接创建/编辑组织个体 | 双写必冲突；组织模块是唯一主源；本期不产生组织个体 |

| 8 | 推理机/自动物化 `ancestorOrg` | 本仓 V1 无推理机；层级查询走递归/闭包，OWL 导出保留传递公理 |

| 10 | 指标/KPI 本体（销售额、出租率、客流） | 属于观测/指标域，不塞进组织类 |

### 2.3 四个关键矛盾

1. **枚举表达力不足**：没有 `GROUP`/`STORE`；`SUBSIDIARY`/`BRANCH` 前后端不一致。
2. **类层级 ≠ 组织树**：不能把“区域”建成“集团”的子类；实际上下级是 `parentOrg` 个体关系。
3. **租户 vs 平台**：组织是租户级，本体是平台级；同一个 `code` 在多个租户可重复，而本体个体编码要求全局唯一。
4. **硬删除 vs 同步**：组织删除不写 `deleted_at`，同步不能靠软删时间戳发现删除，必须用映射表孤儿扫描或删除前事件。

## 3. 关键架构决策（ADR）

### D1. 组织模块为事实主源，本体是只读投影（AI 同步阶段原则，本期不实现）

- 本期不产生 ABox；后续 AI 同步时，组织单元/用户/职位仍在业务模块 CRUD，本体只读投影。
- 本体页面不手工创建组织个体；已同步个体只读。
- **否决双向同步**：组织树、租户、权限、审计均在业务侧；本体写回会绕过业务校验，且两端版本冲突无法自动合并。

### D2. 类型用类表达，不建 `orgType` 数据属性

- 本期只把现有 8 个 `type` 做**展示映射**；`subtype` 延后。
- 后续同步时 `type`/`subtype` → 本体类；原始枚举值放 `orgTypeCode`/`orgSubtypeCode` 注解，供溯源与回查。
- **否决只建 `orgType` 字符串属性**：那样类型无法参与类层级、不相交、专属属性与 OWL 导出，等于把 CRUD 枚举搬进本体。

### D3. 本期零表结构、零扩展字段、零枚举改动

- 不新增 `sys_org_units` 列/子表/JSONB；不改 `type` 枚举；不建同步映射表。
- 表单只做 `label` 展示关联，`value` 仍是现有枚举，不落类 ID。
- 后续 `subtype`/17 个扩展字段必须单独评审，不能以“顺手”方式夹带进本期。

### D4. 本期不做同步实现，后续由 AI 驱动

- 不写 worker/outbox/回填，不做组织个体投影。
- AI 可以替代 worker，但不能替代契约：建议本期先写机器可读映射配置与 runbook（可选），后续 AI 只调现有个体 API/域内核。
- 确定性 worker/映射表仅作为未来 fallback，不是本期交付。

### D5. AI 同步身份用稳定合成码

- `ontologyCode = "T{tenantId}-ORG-{orgId}"`；原始业务编码放 `sourceCode` 注解。
- **理由**：AI 可按 `T{tenantId}-ORG-` 前缀列出某租户全部组织个体，做全量对账/孤儿检测，不依赖映射表；组织改码不破身份。
- 个体 localName 仍由 06 期自动生成（如 `i000123`）；不把业务编码塞进 IRI。

### D6. 同步个体只读，不参与本体侧人工编辑（AI 同步阶段）

- 个体页显示“来源：组织架构”徽标；编辑/删除禁用；后端 BFF 守卫拒绝用户修改。
- 需要改组织信息回 `/opm/org-units`。
- 远期提供“解除同步”（detach）：移除 `sourceSystem/sourceId/tenantId` 注解并把映射置 `DETACHED`，之后允许人工编辑；本期不做。

### D7. 组织删除 = 本体个体废弃，不是硬删除个体（AI 同步阶段）

- 组织是硬删除；AI/同步阶段用“当前组织快照 vs 按编码前缀列出的组织个体”差集发现删除，把对应个体 `deprecated=true`，保留编码、类型、断言和历史引用。
- 组织恢复（同 ID 重新出现）时取消废弃并更新。
- **否决 `force=true` 硬删除个体**：会级联删 61 引用，破坏历史与审计；组织删除本就不应放大成知识库级联删除。

### D8. 人员/职位同步延后

- 本期只建 `Person`/`User`/`Position` 类，不产生个体。
- 人员和职位同步、`hasLeader`/`hasContact`/`holdsPosition` 等断言留到 AI 同步阶段；在此之前负责人/联系人可用 `leaderName`/`contactName` 注解过渡。
- 用户 PII 最小化：默认不同步 email/mobile。

### D9. “展示关联”不是级联选择

- 表单 `value` 仍是 `COMPANY`/`STORE`/`DEPARTMENT` 等现有枚举；`label` 可显示“门店（Store）”“法人单位（LegalEntity）”。
- 不提交类 ID、不落库、不做第二级选择；列表筛选、编辑回显、存量数据不变。
- 级联选择（`type → 类/业态/职能`）需要 `subtype`/`class_id` 字段，属于后续扩展，不在本期。

```
      │  │  └─ GeneralManagerOffice 总经办
      │  ├─ Division 事业部
      │  ├─ Committee 委员会
      │  ├─ Team 团队
      │  └─ OtherOrgUnit 其他组织
      ├─ Person 人员（抽象）★新增
      │  └─ User 用户（⊑ Person）★新增
      └─ Position 职位/岗位（对应 sys_positions）★新增
```

**命名说明：**

- `OrgElement` 沿用 UOM 文档预留的“组织要素”域根，也是源项目 `OrgElement`（206）的等价物；显示名写“组织架构”或“组织要素”，二选一。
- `OrgUnit` 对应 `sys_org_units` 一行；所有管理类型都 `⊑ OrgUnit`。中间这层不能省：`parentOrg`、`code`、`orgStatus`、地址等公共属性只挂一次。
- `LegalEntity` 是用户拍板的“单位”；但**分公司通常不是独立法人**，所以类注释必须写清：本类承载“依法登记的经营主体”，`isLegalEntity` 区分是否独立法人；如果法务口径要求严格，二期再拆 `LegalPerson` / `RegisteredBranch`。
- `Position` 对应本仓 `sys_positions`“职位表”；源项目叫 `Post`（岗位），语义对齐，类名按本仓命名。
- `Unit` / `Units` 已被计量域占用（302/304），组织域禁用这两个 localName。

### 4.6 不相交、多类型与命名规则

**不相交只落高价值对，不做全配对：**

- `Group ⊥ Store`、`Group ⊥ Department`、`Group ⊥ Project`
- `Region ⊥ Store`、`Region ⊥ Department`、`Region ⊥ Project`
- `Store ⊥ Department`、`Store ⊥ Project`、`Department ⊥ Project`
- `Person ⊥ OrgUnit`、`Person ⊥ Position`、`OrgUnit ⊥ Position`（源项目同款；`User ⊑ Person` 继承）
- 顶层：`OrgElement ⊥ Units`（2 行），保证组织域与计量域根不混

**明确不声明：**

- `Group ⊥ LegalEntity`、`Region ⊥ LegalEntity`：集团/区域公司可能就是法人。
- 门店业态子类之间：综合体可能同时是购物中心+百货。
- 部门职能子类之间：现实存在混合部门。
- `OtherOrgUnit` 与其他类：避免临时多类型冲突，靠治理规则尽快归类。

**多类型用法：** 主类型 `sort_order=0`，次要类型 `sort_order>0`。例：

- 某某集团：`Group`（主）+ `LegalEntity`（次，若集团是签约主体）
- 某某区域公司：`Region`（主）+ `LegalEntity`（次）
- 某某综合体：`ShoppingMall`（主）+ `DepartmentStore`（次，若含百货）
- 某某门店独立法人：`Store`（主）+ `LegalEntity`（次）

**命名规则：**

- 类 UpperCamelCase，属性 lowerCamelCase，命名空间沿用 `https://youmingwanwu.com/ontology/youmingwanwu#`。
- 中文名走 `rdfs:label`，语义边界/对应枚举/典型实例走 `rdfs:comment`。
- 不为实际门店/公司/部门名建类；实际组织行是个体。
- 不用 `Unit` 表示组织“单位”；不用 `subClassOf` 表示上下级。

### 5.2（后续）两级类型：`type + subtype`

**一条原则**：`type` 回答“这是什么管理节点”，`subtype` 回答“在该类型下是哪一种”。不在 `type` 里堆 26 个叶子值。

| `type` | `subtype` 词表 | 是否必填 | 本体映射 |
|---|---|---|---|
| `STORE` | `DEPARTMENT_STORE` / `SHOPPING_MALL` / `COMMUNITY_COMMERCIAL` / `OUTLET_STORE` / `STREET_COMMERCIAL` / `MIXED_USE_COMPLEX` / `OTHER` | 是 | 叶子类；`OTHER`/空 → `Store` |
| `DEPARTMENT` | `LEASING` / `OPERATIONS` / `MARKETING` / `CUSTOMER_SERVICE` / `FINANCE` / `HR_ADMIN` / `ENGINEERING_PROPERTY` / `SECURITY` / `IT` / `GM_OFFICE` / `INVESTMENT` / `ASSET_MANAGEMENT` / `LEGAL_COMPLIANCE` / `AUDIT` / `OTHER` | 是 | 叶子类；`OTHER`/空 → `Department` |
| `PROJECT` | `PRE_OPENING` / `RENOVATION` / `ASSET_LIGHT` / `SPECIAL` / `OTHER` | 是 | 统一 `Project`；`subtype` → `projectType` 数据属性 |
| `DIVISION` | `DEPARTMENT_STORE` / `SHOPPING_MALL` / `OUTLET` / `ASSET_LIGHT` / `OTHER` | 否 | 统一 `Division`；`subtype` → `businessLine` |
| `COMMITTEE` | `LEASING_DECISION` / `BRAND_REVIEW` / `SAFETY` / `COMPENSATION` / `INVESTMENT` / `OTHER` | 否 | 统一 `Committee`；`subtype` → `committeeType` |
| `TEAM` | `LEASING` / `OPERATIONS` / `ENGINEERING` / `OTHER` | 否 | 统一 `Team`；`subtype` → `teamType` |
| `GROUP` / `REGION` / `COMPANY` / `SUBSIDIARY` / `BRANCH` / `OTHER` | 无 | 否（必须为空） | 直接映射 |

**为什么不用 JSONB/`attributes` 承载细分**：

- 细分类型要参与后端校验、列表筛选、本体类映射；字符串 JSON 会把这些都变成手写逻辑。
- `type + subtype` 是有限受控词表，用后端白名单 + 前端字典最稳。
- 长尾自定义字段后续再考虑 `attributes` JSONB；核心字段仍用显式列。

> **词表与 TBox 同步纪律**：新增/启用一个 `STORE`/`DEPARTMENT` 的 subtype 前，先落对应本体叶子类；TBox 暂时缺类时，同步器回退父类（`Store`/`Department`）+ `orgSubtypeCode` 注解并记 WARN，不阻塞组织录入，但不能长期缺类。

### 5.7（后续）后端校验与规范化

新增一个 `OrgUnitTypePolicy`（服务层纯函数/配置），负责：

1. **允许的 subtype**：`type → []subtype` 白名单；不在白名单 → 422。
2. **必填 subtype**：`STORE/DEPARTMENT/PROJECT` 必须非空。
3. **必填字段**：按 5.4 矩阵校验（如 STORE 必须有 `opening_date`、`address`；法人必须有 `registration_number`/`tax_id`）。
4. **父子类型**：按 5.5 矩阵校验，禁止自环/挂到自身后代（repo 已有路径环检测，服务层前置更友好）。
5. **法人一致性**：
   - `COMPANY/SUBSIDIARY` → `is_legal_entity=true`；
   - `BRANCH` → `is_legal_entity=false`（但仍在 `LegalEntity` 类）；

   - 其他类型 `is_legal_entity=true` 时 `legal_form` 必填；
   - `legal_entity_org_id` 必须指向 `LegalEntity` 类型节点，不能指向自身。
6. **日期校验**：`start_at <= end_at`；项目必须两者都有。
7. **字段清理/规范化**：
   - 类型不适用字段置空（不是保留旧值）；
   - `subtype` 不适用的类型必须为空；
   - `is_legal_entity=false` 时 `legal_form` 置空；
   - `BRANCH` 的 `legal_entity_org_id` 建议指向母公司；`STORE/DEPARTMENT` 建议必填（业务可配置）。

> **实现坑（必须写进实现任务）**：当前 `OrgUnitRepo.Update` 用 `SetNillableXxx`，nil 值不会清空旧字段。动态表单切换类型后要清空不适用字段，必须显式 `ClearXxx()` 或走“读旧行 → 合并 → 整体写”的规范化路径；否则切换类型后旧门店字段会留在库里，UI 不显示但同步会照旧映射。

## 6. 组织个体同步设计（后续 AI 同步阶段；本期不实现）

> **V1.1 范围声明**：本节 6.1~6.13 是确定性同步的参考实现（worker/映射表/限速/重试等），**本期不交付**。本期只交付 6.0 的 AI 同步契约与 runbook；AI 可以复用现有个体 API，也可以在未来选择下面的 worker 方案作为 fallback。

### 6.0 AI 同步契约（后续设计；本期不实现，建议先写最小版）

AI 同步可以不做自定义 worker，但至少要确定以下契约，否则 AI 只能靠猜：

1. **机器可读映射配置**（YAML/JSON，入库或放代码库均可，需版本化）：
   - `type → 类 localName/IRI`；
   - `字段 → 本体数据属性/对象属性 localName`；
   - 编码规则、租户规则、必填/可空规则。
2. **稳定身份**：`code = T{tenantId}-ORG-{orgId}`；`sourceSystem`/`sourceId`/`tenantId`/`sourceCode` 注解。AI 按 `T{tenantId}-ORG-` 前缀列出某租户全部组织个体，做全量对账和孤儿检测，不依赖映射表。
3. **写入工具**：AI 只调现有个体 API/域内核（Create/Update/Frame/List/废弃），**不直接写 `ont_*` 表**；否则绕过乐观锁、校验与变更日志。
4. **校验**：类/属性白名单、必填字段、租户隔离、跨租户父/法人解析拒绝、dry-run 报告。
5. **孤儿策略**：当前组织快照 vs 按编码前缀列出的个体列表；差集 → `deprecated=true`，不硬删。
6. **建议本期先写**：映射配置、AI runbook、样例 payload、校验清单（可选）；**不跑批量同步、不建映射表、不写 worker**。

**AI 首版的能力边界（没有 subtype/扩展字段）：**

- `STORE` 只能落 `Store`；不能区分百货/购物中心（叶子类先预留）。
- `DEPARTMENT` 只能落 `Department`；不能区分招商/营运（叶子类先预留）。
- `GROUP`/`STORE` 本期没有枚举值，类先空置；如果生产组织表里已有用 `OTHER` 表达的门店，不要靠 AI 猜，先接受“无法落 Store”。
- 门店面积/开业日期、部门成本中心、项目状态等扩展字段本期没有，不能写进本体。
- 负责人/联系人先写 `leaderName`/`contactName` 注解；`hasLeader`/`hasContact` 等人员同步后再补。

### 6.1 同步边界与主源

| 层 | 主源 | 同步方向 | 说明 |
|---|---|---|---|
| TBox（类/属性/公理） | 本体模块 | 双向都不是 | 本体页面/种子维护；同步器只读 |
| ABox（组织单元个体） | `sys_org_units` | 组织 → 本体，单向 | 组织模块建/改/删；本体只读投影 |
| ABox（用户/职位个体） | `sys_users` / `sys_positions` | 业务 → 本体，单向 | 后续 AI 同步阶段 |
| 关系断言 | 业务表 | 业务 → 本体，单向 | `parentOrg`/`belongsToLegalEntity`/`hasLeader`/`holdsPosition` 等 |

**唯一入口**：组织单元在本体页面不可创建；已同步个体不可编辑/删除。这样避免“本体改一次、下次同步被覆盖”的隐性冲突。

### 6.2 身份与编码（AI 同步契约）

| 项 | 规则 |
|---|---|
| 个体 IRI/localName | 由 06 期取号器自动生成（如 `i000123`）；**不把业务编码塞进 IRI** |
| 本体编码 `code` | 稳定合成码 `T{tenantId}-ORG-{orgId}`；**不用业务 code** |
| 业务编码 | `sourceCode` 注解保存 `sys_org_units.code` 原值；可读展示用它 |
| 来源主键 | `sourceId` 注解 = 组织主键；`tenantId` 注解 = 租户；映射表可选 |
| 个体显示名 | `rdfs:label` = `sys_org_units.name` |
| 个体注释 | `rdfs:comment` = `description`（空则 `remark`） |
| 编码变更 | 组织 `code` 变化**不改**本体 `code`；只更新 `sourceCode` 注解，身份不变 |
| 删除 | 个体不删除；`deprecated=true`；编码保留、号不回收 |

**为什么用租户前缀 + orgId：**

- `sys_org_units` 唯一约束是 `(tenant_id, code)`；两个租户都叫 `HQ-001` 是合法的。
- 本体 `code` 唯一性是“同本体 + 同编码属性 + 值”全局唯一；不加租户前缀，第二个租户同步必撞 `INDIVIDUAL_CODE_DUPLICATE`。
- **用 orgId 而不是业务 code**：AI 可以按 `T{tenantId}-ORG-` 前缀列出某租户全部组织个体，做全量对账/孤儿检测；组织改码不会让 AI 找不到旧个体，也不需要映射表。
- 用 `tenant_id` 而不是租户名称/租户 code（`sys_tenants.code` 未唯一），避免改名/重码导致编码漂移。
- 如果未来要人类可读编码，放到 `sourceCode` 注解或 display label，不要动身份码。

### 6.5 同步触发与调度（确定性 fallback，本期不交付）

> 以下 worker/周期调度是“没有 AI 时”的确定性参考实现；如果由 AI 执行，可省略 worker/映射表，但 6.0 的契约不变。

**确定性 fallback 推荐组合：**

1. **周期增量对账（主）**：服务内后台 runner，每 `org.ontology.sync.interval`（默认 60s）跑一次；用 PostgreSQL advisory lock（如 `pg_try_advisory_lock(hashtext('org_ontology_sync'))`）保证多实例只有一个 scanner。
2. **CRUD 后 best-effort 触发（辅）**：组织创建/更新/删除成功后，异步投递单条同步任务（asynq 可用则入队，不可用则丢给本地 goroutine）；失败不影响业务，由周期对账兜底。
3. **手动全量重建**：平台管理员在同步管理页/接口触发；异步执行，可 dry-run。
4. **每日全量对账（可选）**：周期增量之外每天一次全量扫描，修复漏水/哈希漂移。

**为什么不把 asynq 作为唯一调度：**

- `server.asynq.uri` 未配置时，任务子系统整体静默缺失；组织本体同步不能因此停摆。
- 周期 runner 独立于 asynq；asynq 只用于“尽快同步”的可选加速。

### 6.6 增量对账算法

> AI 版可以把下面的 `mapping` 查询替换为“按 `T{tenantId}-ORG-` 前缀列个体 + 与组织快照比对”，算法其余部分（创建/更新/孤儿废弃）不变。

```
SyncIncremental(now):
  1. 前置检查：ontology(7) 存在；TBox 必需类/属性齐全；否则记录 DISABLED_MISSING_SCHEMA 并退出
  2. 取水位：watermark = max(mapping.source_updated_at) - overlap(10min)
     - 映射表为空/首次运行 → 直接走全量（watermark = 0），不要只扫最近 10 分钟
     - 水位统一用 UTC；overlap 用于兜住时钟偏差/同秒更新
  3. 扫描活动组织：
     SELECT * FROM sys_org_units
     WHERE updated_at >= watermark
     ORDER BY depth(path), id
     对每行：
       payload = BuildPayload(org)
       map = mapping(tenant_id, org_id)
       if map == nil:
          map = enqueue(PENDING, payload_hash)
       else if map.payload_hash != payload.hash || map.sync_status in (PENDING, FAILED):
          map = enqueue(PENDING, payload_hash)
  4. 孤儿扫描：
     SELECT m.* FROM sys_org_ontology_map m
     LEFT JOIN sys_org_units o ON o.id = m.org_unit_id AND o.tenant_id = m.tenant_id
     WHERE o.id IS NULL AND m.sync_status != 'ARCHIVED'
     → enqueue(PENDING_ARCHIVE)
  5. 按 mapping 状态处理（可多 worker，SKIP LOCKED）：
     PENDING          → SyncUpsert
     PENDING_ARCHIVE  → SyncArchive
  6. 记录 run 摘要（扫描/新增/更新/跳过/废弃/失败）
```

**`SyncUpsert`：**

```
1. 解析目标类/属性 ID（缓存；缺失 → FAILED + CLASS_NOT_FOUND/PROPERTY_NOT_FOUND）
2. 按 mapping 找个体；没有则按 ontologyCode 查 code 精确匹配：
   - 找到且 sourceId/tenantId 匹配 → 收养并写 mapping
   - 找到但不匹配 → 编码加 -{orgId} 重试
   - 没找到 → Create（类型+code+label/comment+注解）
3. Frame 取 base_version
4. Update（全量）：
   - main_class_id / type_ids
   - display_label / comment
   - code（仅变化时）
   - data_assertions（全量）
   - object_assertions（全量；父/法人/负责人目标未同步时先跳过，第二轮补）
   - annotations（全量受管注解）
5. 成功 → mapping SYNCED + payload_hash + synced_at
   版本冲突 → 重取 Frame 重试（最多 N 次，指数退避）
   其他失败 → FAILED + last_error + retry_count++
```

**两轮原因：**

- 第一轮先保证所有个体存在（创建父节点、法人节点）；
- 第二轮再补 `parentOrg`/`belongsToLegalEntity`/`hasLeader`/`hasContact` 等对象断言，避免“父个体还没建”的依赖失败。
- 增量单条创建时，若父/目标已存在可一轮完成；目标不存在则先记 `PENDING_DEPENDENCY`，下一轮补。

**`SyncArchive`：**

```
1. Frame 取个体；不存在 → mapping ARCHIVED
2. Update deprecated=true（保留类型/编码/断言）
3. mapping ARCHIVED + archived_at
4. 若组织同 id 重新出现（恢复/备份回滚）→ 下一轮 SyncUpsert 会把 deprecated 改回 false
```

**状态机：**

```
PENDING ──claim──> SYNCING ──成功──> SYNCED
SYNCING ──失败──> FAILED ──重试──> SYNCING
SYNCED ──源删除──> PENDING_ARCHIVE ──成功──> ARCHIVED
ARCHIVED ──源恢复──> PENDING
FAILED ──超过重试上限──> DEAD（人工重试）
```

### 6.7 删除、停用、恢复语义

| 组织动作 | 本体动作 | 理由 |
|---|---|---|
| 组织 `status=OFF` | 个体保留，`orgStatus=OFF` | 停用不是删除；历史关系仍需可查 |
| 组织硬删除（含子树） | 个体 `deprecated=true`，mapping `ARCHIVED` | 保留历史、编码和引用；不级联删 61 |
| 组织恢复（同 ID） | 取消 `deprecated`，更新断言 | 备份回滚/误删恢复 |
| 项目结束 | `projectStatus=CLOSED` + `validTo`；不废弃 | 项目组织生命周期结束，但历史可查 |
| 类型变更 | `main_class_id`/`type_ids` 全量替换 | 06 期类型区专用 diff；主类目变更不改码 |
| 编码变更 | 更新 `code`，原始码进 `sourceCode` 注解 | 06 期支持改码；引用用个体 ID 不迁移 |
| 租户删除/到期 | 孤儿扫描最终废弃该租户全部个体 | 租户清理会删组织；同步跟随 |

### 6.8 失败重试与可观测性

**错误码（建议）：**

| 错误 | 含义 | 处置 |
|---|---|---|
| `ORG_SYNC_DISABLED_MISSING_SCHEMA` | TBox 缺类/属性 | 先落 TBox 种子；同步暂停并告警 |
| `ORG_SYNC_CLASS_NOT_FOUND` | 目标类不存在 | 检查 TBox/子类映射 |
| `ORG_SYNC_PROPERTY_NOT_FOUND` | 目标属性不存在 | 检查 TBox 种子 |
| `ORG_SYNC_CODE_INVALID` | 编码规范化后仍非法 | 修正组织 code 或检查规范化规则 |
| `ORG_SYNC_CODE_DUPLICATE` | 编码冲突 | 追加 `-{orgId}` 或修数据 |
| `ORG_SYNC_PARENT_NOT_SYNCED` | 父个体未同步 | 下一轮重试/先同步父 |
| `ORG_SYNC_LEGAL_ENTITY_NOT_SYNCED` | 法人个体未同步 | 下一轮重试/先同步法人 |
| `ORG_SYNC_ONTOLOGY_VERSION_CONFLICT` | 本体乐观锁冲突 | 重取 Frame 重试；持续冲突则降速/暂停 |
| `ORG_SYNC_SOURCE_DRIFT` | 受管个体被绕过只读守卫修改 | 以业务侧为准覆盖并记 WARN；排查绕过入口 |

> 用户请求编辑受管个体时的拒绝码是 `ORG_SYNC_INDIVIDUAL_MANAGED`（BFF 守卫），与同步器内部的 `ORG_SYNC_SOURCE_DRIFT` 不是同一个语义，勿混用。

**可观测性：**

- 映射表 `sync_status` / `last_error` / `retry_count` / `synced_at`。
- 同步 runner 结构化日志：`run_id`、扫描数、创建/更新/跳过/废弃/失败数、耗时。
- 组织列表显示同步状态徽标（已同步/待同步/失败/已归档）；失败 tooltip 显示错误；平台管理员可单条重试。
- 同步管理页/标签页：最近运行摘要、失败清单、dry-run、全量重建、重试失败。
- 可选：连续 N 次失败或超过 2 个周期未成功，给平台管理员发站内信（复用通知域）。

### 6.9 多租户隔离

- 本体是平台级；映射表带 `tenant_id`，唯一键 `(tenant_id, org_unit_id, ontology_id)`。
- 同步 runner 用 `viewer.WithSystemContext` 跨租户扫描；所有父/法人/负责人解析都带 `tenant_id`，禁止跨租户关联。
- 个体编码前缀 `T{tenantId}-`；`tenantId` 注解；`sourceId` 单独不唯一。
- 平台管理员可在本体页看到全部租户个体；如需租户级隔离，二期按 `tenantId` 注解做视图过滤。
- 不要把租户名称/租户 code 拼进本体编码：租户可改名/重码；用 `tenant_id` 稳定。

### 6.10 权限与只读投影

| 动作 | 权限 | 行为 |
|---|---|---|
| 组织 CRUD | 现有组织模块权限 | 不变；同步异步执行，不阻塞业务 |
| 同步管理/重试/全量重建 | `sys:platform_admin` | 新增权限点/菜单；Api 表登记新端点 |
| 本体类/属性编辑 | 现有平台管理员 | 不变；同步器只读 TBox |
| 本体个体编辑/删除（受管） | 禁止 | 后端校验 `sourceSystem` 注解；返回 `ORG_SYNC_INDIVIDUAL_MANAGED` |
| 本体个体查看 | 现有平台管理员 | 显示来源徽标 + “在组织架构中打开”链接 |
| 解除同步（P5） | `sys:platform_admin` | 移除受管注解 + mapping `DETACHED`；之后允许人工编辑 |

**只读保护实现要点：**

- 个体 `sourceSystem` 注解是判定依据；不要只看 `code` 前缀（用户可能手工建同码）。
- **只读守卫放在 BFF/HTTP 入口，不放在领域内核**：`OntologyIndividualService.Update/Delete` 是用户入口，查询 `sourceSystem` 注解后拒绝受管个体；同步器不能走这个入口，否则它自己也会被挡住。
- 同步器走**内部写入通道**：复用 06 期的变更集组装/`ApplyInTx`，或提供一个只对服务内可见的 `ManagedIndividualWriter`；它跳过“受管只读”守卫，但仍走乐观锁、校验、变更日志。
- 若不想拆两套方法，可用显式内部上下文标记（如 `ontology.WithManagedWrite(ctx)`）让守卫区分“用户请求”与“同步写入”；**不要用“是否 SystemContext”作为唯一判据**——同步和平台管理员请求都可能是 SystemContext。
- 前端隐藏编辑/删除按钮只是体验，不是安全边界。

### 6.11 人员/职位/任职同步（后续 AI 同步阶段）

**同步顺序**：组织单元 → 职位 → 用户 → 任职关系/负责人/联系人。

| 源表 | 目标类 | 编码 | 关键断言 |
|---|---|---|---|
| `sys_positions` | `Position` | `T{tenantId}-P-{positionId}` | `positionOfOrg`、`reportsToPosition` |
| `sys_users` | `User` | `T{tenantId}-U-{userId}` | `primaryOrg`、`memberOfOrg`、`holdsPosition` |
| `sys_user_org_units` | — | — | `memberOfOrg`（按 `status=ACTIVE`、有效期过滤） |
| `sys_user_positions` | — | — | `holdsPosition`（按 `status=ACTIVE`、有效期过滤） |
| `sys_org_units.leader_id` | — | — | `hasLeader` |
| `sys_org_units.contact_user_id` | — | — | `hasContact` |

**规则：**

- `User ⊑ Person`，本期不单独建 `Person` 个体；用户即人员的具体身份。
- 用户编码用稳定主键 `T{tenantId}-U-{userId}`，不要用 username（可改）。
- 职位编码用 `T{tenantId}-P-{positionId}`；`code`/`name` 作为数据属性。
- 任职关系只同步 ACTIVE 且当前有效的行；历史任职不进 ABox（保留在业务表）。
- 用户/职位删除 → 个体废弃；停用 → 状态数据属性。
- PII 最小化：默认不同步 email/mobile；如业务确需，另做字段级权限/脱敏。
- 人员同步前，组织的 `hasLeader`/`hasContact` 先不同步；用 `leaderName`/`contactName` 注解过渡。

### 6.12 并发、吞吐与多实例

**必须正视的性能约束：**

- 06 期每个个体 Create/Update 都会锁本体行并递增本体 `version`；同步大量个体时是**串行写**，还会与本体页面的类/属性编辑争锁。
- AI/同步首版不要并发猛灌。建议：
  - 同步 runner 单写者，`maxWritesPerSecond`（默认 5~10）限速；
  - 初始全量在维护窗口跑；
  - 版本冲突指数退避重试；连续冲突则暂停并告警；
  - 增量每轮只处理变化行，正常量很小。
- 10k 组织按 5 条/秒全量约 33 分钟；可接受则一期不做批量；若要求更快，后续阶段设计 `ApplyBatch`（一次锁本体行、批量变更、单次 version 递增），作为独立能力评审。
- 多实例：
  - scanner 用 advisory lock 保证单实例；
  - worker 用 `SELECT ... FOR UPDATE SKIP LOCKED` 认领 mapping 行，可多实例；
  - 单实例部署可简化为一锁到底。
- 映射表 `payload_hash` 避免“每轮全量 Update”；未变化直接跳过。

### 6.13 个体与 TBox 缓存

- 同步器启动时加载 TBox 索引：`localName → entity_id`（类/对象属性/数据属性/注解属性）。
- **不要用本体 `version` 做 TBox 缓存 key**：每次个体写入都会 bump version，会导致缓存每轮失效；用 TTL（如 5 分钟）+ 未命中重载。
- 缺类/缺属性时不要“部分同步”：直接标记 `DISABLED_MISSING_SCHEMA`，等 TBox 补齐后重跑，避免 ABox 半成品。

### 6.14 AI 同步 runbook（后续设计；建议本期先写，不执行）

**AI 输入：**

1. 当前租户的活动组织快照：`id/name/code/type/parent_id/status/...`（现有字段）。
2. 已有个体列表：按 `code` 前缀 `T{tenantId}-ORG-` 分页拉取；记录 `code/sourceId/deprecated`。
3. 映射配置：`type → 类 localName/IRI`、`字段 → 属性 localName`、编码/租户规则。

**AI 输出（先 dry-run）：**

对每个组织输出一个结构化计划：

```json
{
  "orgId": 1024,
  "tenantId": 12,
  "ontologyCode": "T12-ORG-1024",
  "primaryClass": "Store",
  "secondaryClasses": [],
  "label": "某某购物中心",
  "comment": "……",
  "dataAssertions": [
    {"property": "orgStatus", "value": "ON"},
    {"property": "isLegalEntity", "value": "false"}
  ],
  "objectAssertions": [
    {"property": "parentOrg", "targetOntologyCode": "T12-ORG-8"},
    {"property": "belongsToLegalEntity", "targetOntologyCode": "T12-ORG-10"}
  ],
  "annotations": {
    "orgTypeCode": "STORE",
    "sourceSystem": "sys_org_units",
    "sourceId": "1024",
    "tenantId": "12",
    "sourceCode": "XMALL-001"
  },
  "action": "CREATE | UPDATE | SKIP"
}
```

**执行顺序：**

1. dry-run：只读 org 快照 + 个体列表，产出计划；不写。
2. 校验：类/属性必须在白名单；父/法人目标必须在同租户且已存在；编码不冲突；没有扩展字段。
3. 应用：第一轮 Create 缺失个体（类型/编码/label/comment/注解）；第二轮 Update 补数据/对象断言；版本冲突重试。
4. 孤儿：计划中标记 `action=ARCHIVE` 的个体 → Update `deprecated=true`；不硬删。
5. 报告：创建/更新/跳过/废弃/失败数量 + 错误明细；失败可重跑（幂等）。

**硬约束：**

- AI 只调权限受控的个体 API/工具，不直接写 `ont_*` 表。
- AI 不推断 `subtype`/业态/职能；没有字段就不写叶子类。
- AI 不编造门店面积、开业日期、部门成本中心等当前不存在的字段。
- AI 不跨租户解析父/法人；所有查询带 `tenantId`。
- AI 不删除个体；只废弃。
- 批量首跑先选一个租户/一个小组织树试点，人工看 dry-run 报告后再执行。

- OWL 导出全量编译通过作为验收项。

### 7.7（后续）同步 worker 装配

> 本期不写 worker；如果后续由 AI 同步，本节仅作为确定性 fallback 参考。

- 新增 `OrgOntologySyncRunner`（后台周期 runner），在服务启动后启动、关闭时停止；配置项：
  - `org.ontology.sync.enabled`（默认 false，灰度开关）
  - `org.ontology.sync.ontology_id`（默认 7）
  - `org.ontology.sync.interval`（默认 60s）
  - `org.ontology.sync.batch_size`（默认 200）
  - `org.ontology.sync.max_writes_per_second`（默认 5）
  - `org.ontology.sync.max_retries`（默认 8）
  - `org.ontology.sync.overlap`（默认 10min）
- CRUD 后 best-effort 触发：可在组织 service 成功后投递；不放在 repo 事务里，避免把同步失败回滚成业务失败。
- **同步上下文**：用 `viewer.WithSystemContext` 跨租户扫描，并注入固定同步操作人（如 `admin` 用户 ID 1）供变更日志/审计追溯；不要用随机用户，也不要依赖 operator=0（部分日志/审计链路对 0 不友好）。
- 如用 asynq：注册系统级任务类型 `org_ontology_sync`，在 `startAllTask` 末尾注册周期；handler 在 `NewAsynqServer` 注册。**周期 runner 仍是兜底**，不依赖 asynq。
- 多实例：scanner 用 PostgreSQL advisory lock（注意会话级锁要固定在专用连接上，或改用 `sync_lease` 行 + `FOR UPDATE`）；worker 用 `SELECT ... FOR UPDATE SKIP LOCKED` 认领 mapping 行；租约超时回收 `SYNCING` 行。

- 组织模块原有权限不变；本体类页面沿用现有平台管理员权限。
