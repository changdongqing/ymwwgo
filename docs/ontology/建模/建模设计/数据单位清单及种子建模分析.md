## 1. 三套参考库的阅读结论

### 1.1 QUDT 3.4.0 —— 单位与量纲的权威库（本清单主要来源）

- **规模**：`qudt-all.ttl` 内含 **2 925 个单位个体**（`qudt:Unit`）、**1 218 个量纲类型**（`qudt:QuantityKind`）、20 个 SI 词头（`qudt:Prefix`）、单位制（`sou:SI` 等）。全量照搬不可行，必须按领域裁剪。
- **单位个体的建模字段**（以 `unit:DEG_C` 为样板）：
  - `qudt:symbol`（显示符号 "°C"）、`qudt:ucumCode`（UCUM 交换码 "Cel"，跨库对齐的事实键）
  - `qudt:hasQuantityKind` → 挂量纲（一个单位可挂多个：DEG_C 同时挂 Temperature/FlashPoint/…）
  - `qudt:conversionMultiplier` / `qudt:conversionOffset`（SI 换算：°C = K × 1 + 273.15）
  - `qudt:scalingOf`（派生自哪个基准单位）、`qudt:hasDimensionVector`（量纲向量）
- **量纲层级**用 `qudt:specializationOf`（skos:broader 的子属性）表达，如 `GaugePressure ⊑ Pressure ⊑ ForcePerArea`、`LiquidLevel ⊑ Length`、`ThermalEnergy ⊑ Energy`、`BatteryCapacity ⊑ ElectricCharge`。
- **关键发现——QUDT 已为楼宇场景预留了冷门单位**：`unit:PERCENT_RH`（%RH，量纲 RelativeHumidity）、`unit:PERCENT-PER-M`（%/m，减光率，量纲 AttenuationCoefficient）、`unit:TON_FG`（冷吨）、`unit:MilliM_H2O` / `unit:M_H2O`（毫米/米水柱）、`unit:DeciB_A`（dB(A)）、`unit:PER-HR`（1/h，换气次数）——楼控/消防所需单位在 QUDT 里的覆盖率非常高。

### 1.2 Brick 1.4 —— 楼宇自动化 schema（领域裁剪依据）

- **Brick 不内嵌任何单位**：`unit:` 前缀全部外置引用 QUDT，全文 0 条单位声明，共引用 **198 个 QUDT 单位**。核心模式三层：
  - `brick:hasQuantity`（测点 → 量类型，`rdfs:subPropertyOf qudt:hasQuantityKind`）
  - `brick:hasUnit`（测点/实体属性 → QUDT 单位）
  - `brick:Quantity ⊑ qudt:QuantityKind`（Brick 自有的 52 个楼宇特有量是 QUDT 量纲的子类概念）
- **最重要的领域事实**：HVAC 最常用的量（温度、湿度、风量、电压、电流、功率、照度、露点……）Brick 不自建，而是让测点直接引用 QUDT 的 `quantitykind:`——**通用量以 QUDT 为准，Brick 只补楼宇特有量**（差压 `Differential_Static_Pressure`、差温 `Differential_Temperature`、阀门开度 `Position`（单位 %）、占用 `Occupancy_Count` 等）。不在 brick:Quantity、但被 461 个测点类经 `brick:hasQuantity` 直接使用的 QUDT 量类型按引用次数排序：Temperature(145)、VolumeFlowRate(57)、RelativeHumidity(18)、Power(17)、StaticPressure(15)、Pressure(14)、Dimensionless(13)、DewPointTemperature(7)、Time(6)、Frequency(6)、ElectricCurrent(6)、Voltage(5)、Enthalpy(5)、Volume(4)、DynamicPressure(4)、Illuminance(3)、GaugePressure(3)、Energy(3)、Angle(3)、Torque(2) 等。
- **消防在 Brick 中没有专属量纲**：烟感/温感/手报全部建模为设备类（`Smoke_Detector` / `Heat_Detector` ⊑ `Fire_Safety_Equipment`）和布尔报警点（`Alarm`），气体探测复用空气质量量（ppm/ppb/µg/m³）。**结论：消防单位清单 = QUDT 通用物理量 + 极少数特殊量（减光率、声压级），不存在"消防专用单位库"**——这直接影响种子建模的取舍（见 §5）。

### 1.3 CommonCoreOntologies 2.1 —— 测量范式参照（词表不可用）

- **词表规模与覆盖**：全库 **269 个单位个体 + 30 个"某量的单位"类**（可读名只在 rdfs:label，IRI 是不透明的 `ont000XXXXX`）。其中 **128 个是各国货币**，真正物理单位约 141 个，都是教科书级通用单位（m/kg/s/°C/Pa/bar/psi/Hz/RPM/N·m/kVA…）。
- **楼控/消防关键单位全部缺失**：没有 ppm/浓度、没有湿度、没有照度 lux/流明、没有浊度、没有 CO/CO₂ 类气体量、没有 µg/m³ 颗粒物、没有 %RH、没有冷吨。**也没有换算机制**：无词头体系（km、mg 各自独立个体）、无 conversionMultiplier/Offset、连 SI 归属都只是两条注解属性（SI unit label / SI unit symbol）。
- **结论**：CCO 不提供任何清单增补；单位词表以 QUDT 为唯一来源（§6 详述其真正价值）。

### 5.1 结论先行（架构定稿：多顶层类 + 单本体）

### 5.4 关键技术约束与取舍（落地前必读）

1. **IRI 命名空间不能直接用 qudt.org**：本系统硬约束 `实体 IRI = baseIri + localName`（`OntEntityFactory.buildIri`），baseIri 规范化为以 `#` 结尾，而 QUDT 单位 IRI 是斜杠式无 `#`（`http://qudt.org/vocab/unit/DEG_C`）。**方案**：骨架与单位个体全部落在「有名万物」既有命名空间下（**不新建 base_iri**），localName **原样沿用 QUDT 局部名**（`DEG_C`、`KiloW-HR`、`PERCENT_RH`、`M3-PER-HR`…全部匹配 localName 正则），QUDT 原 IRI 以 qudtIri 注解字面量留存。若未来要 qudt.org IRI 保真，可走 07 期 OWL 导入路径（IRI 不受 baseIri 约束）——种子化更可重复、可审查，仍建议种子。
2. **温差单位选择**：DEG_C 的 conversionOffset=273.15 使其不宜作差量单位，供回水温差等 ΔT 测点挂 TemperatureDifference 量纲 + K（或注解注明 ΔT 语义下 DEG_C 数值等效），种子的 rdfs:comment 里写清。
3. **湿度用 PERCENT_RH 不用 PERCENT**：QUDT 专门个体（%RH，挂 RelativeHumidity），避免与开度/载荷等普通 % 混淆。
4. **消防无独立单位库**：Brick 证实消防单位全部复用通用物理量；种子不做"消防单位"子类，消防语义放在量纲与测点层（后续测点建模时以 hasQuantity 区分）。
5. **QUDT 覆盖缺口（种子需注解兜底）**：%LEL、pH、okta（云量）无 QUDT 单位——%LEL 用 PERCENT、pH 用 ONE（0~14 可配 Percent0To100 类似派生类型）+ rdfs:comment 说明；换气次数 PER-HR 的量纲 QUDT 无专用 QK，挂 Frequency 并注解。

### 5.5 多顶层类架构纪律（「有名万物」的演进规则）

本仓定稿：**多顶层类架构 + 单一本体文档**——owl:Thing 之下一个平台薄根类「万物」，其直接子类即各顶层域类（本期：单位 Units 容器类，其下再挂计量单位/量纲类型两个叶子域类；后续组织要素、工种、空间、设备、表单……），每域一枝、同级并列。新增顶层域类时照章执行：

1. **顶层两两不相交是铁律**：每个新顶层类与既有全部顶层类成对落 21 行（双向两行）。k 个顶层类共 k(k-1)/2 对，k=10 时 45 对 90 行，可接受；跨域共性一律走对象属性，**不要**靠一个类多重继承或个体双重类型解决（后者仅在确有依据时使用）。
2. **跨域属性挂「万物」，规避定义域交集陷阱**：OWL 多定义域取交集。跨域数据/对象属性（如"附件""创建人""排序"）的定义域统一声明到万物，不逐域声明；域内专有属性仍挂各自域类。万物类本身刻意零属性、零子类约束，保持"薄根"。
3. **命名与 IRI 纪律**：实体查重是"本体文档内 IRI 查重"，库变大后 localName 撞名（不同域都想叫 status/name）只能靠习惯兜底——属性 localName 带域语义（如 `deviceName`/`spaceName`），类 localName 用域名英文大驼峰，单位沿用 QUDT 局部名。
4. **个体页容量**：单位个体（≈91）进库后有名万物个体从 17 → 160，个体页靠类型过滤（按 Unit/QuantityKind 主类目）消化；类树徽标按直接实例计数，层级不受影响（V1.1 后测试个体 17 个改挂计量单位，Unit 直接实例 108 / QuantityKind 52）。
5. **每域一个增量迁移脚本**：新域照 00003~00005 惯例起独立 goose 脚本（实体/公理分段编配、`ON CONFLICT DO NOTHING`、尾部 setval 校准、不写变更日志），永不回改已提交脚本。

### 5.6 基准单位判定（三层）

「同一量纲哪个单位是基准」不能靠 multiplier=1 反推（kL 与 m³ 同为 1.0、DEG_C 倍率 1 但偏移 273.15、kW·h 族根本没有 1.0 单位、dB 倍率为 0）。定稿为**三层显式化**，各答一个问题：

| 层 | 载体 | 回答的问题 | 语义锚点 |

| ① 惯用基准 | `conventionalUnit`（域=量纲类型、值域=计量单位、函数性 33 号段） | **默认用哪个**——查量纲个体的本属性即得 | 国内楼宇/消防行业点表与规范口径（§下表） |
| ② 换算链定义根 | `scalingOf`（域/值域=计量单位）；**无 scalingOf 的单位即根** | 倍率从哪来——本单位 = 目标 × 倍率(+偏移) | QUDT 原样、SI 锚定（刻意不按习惯改写，否则与 qudtIri 溯源及倍率语义矛盾） |

## 6. CCO 补充结论：测量值的建模范式

CCO 的词表不可用（§1.3），其真正价值是"测量如何落库"的范式与反面教训。

### 6.1 测量范式（四元组）

CCO 不做 reified Quantity，测量 = 信息实体 + 值载体 + 单位个体：

```
被测对象(Quality/Process)
  --is measured by--> 测量内容个体(MICE，描述性信息实体)
  --is concretized by--> 值载体个体(IBE，挂 has decimal value: 25.4)
       <--is measurement unit of-- 单位个体(如 Degree Celsius)
```

映射到本系统：**测值 = 个体（主类目"测值/测点"）+ 62 数据断言存数值 + 61 对象断言经 hasUnit 指向单位个体**——全部落在现有 06 期能力内。

### 6.2 量纲语义放单位侧还是量纲侧

- CCO 靠"Measurement Unit of X"单位类分层承担量纲语义（30 个类），单位个体 type 于 1~3 个单位类；
- QUDT 靠 QuantityKind 个体 + 单位挂接（hasQuantityKind）。
- **本系统选 QUDT 式**：Brick 的测点词汇（`brick:hasQuantity`）就是对齐 `qudt:hasQuantityKind` 的，选 QUDT 才能与 Brick 测点体系直连；CCO 式会让 91 个单位配套的单位类膨胀，而收益仅是少建一层个体。

### 6.3 反面教训：不要建通用"value"数据属性

CCO 2.1 把 1.x 的 `has decimal value / has integer value` 等 8 条泛型值属性**全部 owl:deprecated**（changeNote：应改用领域专属 datatype property 表达"这个数值测的是什么"）。将来落测点/测值建模时应建 `supplyAirTempValue` 这类领域专属数据属性（各自挂 42 值域 + 单位语义），而不是一条通用 `value`。
